# Product Brief: Авторизация и роли модуля «Лазейки» (Authentik)

## Executive Summary

Модуль «Лазейки» — единственная часть AuditLens без реальной идентичности: он доверяет
клиентскому заголовку `X-User-Id`, который любой пользователь может подделать. При этом
модуль содержит разрушительные операции — ручные вердикты по находкам, создание и запуск
парсеров, добавление записей через агента.

Работа переводит модуль на ту же Authentik-идентичность, что и основное приложение
(`get_current_user` из `web/auth.py`), и вводит локальную ролевую модель из трёх ролей:
администратор модуля, сотрудник ЦК КС (методологи, 5–7 человек) и пользователь лазеек
(роль по умолчанию, read-only + скачивание). Маппинг `username → role` хранится локально
в БД и управляется админом через мини-админку — это целевая архитектура, зависимости от
донастройки ОАИТ нет.

Результат: каждая операция модуля проверяется против роли, каждый вердикт имеет автора
и время, раздача прав не требует ни SQL, ни разработчика.

## Проблема

Модуль «Лазейки» идентифицирует пользователя по клиентскому заголовку `X-User-Id`
(`loophole/web.py:42`) — в отличие от основного приложения, которое уже работает через
Authentik forward-auth. Любой сотрудник, прошедший прокси, может подставить чужой ID и
от его имени менять вердикты по лазейкам, создавать и запускать парсеры, добавлять записи
через агента. Одновременно у потребителей данных (аудиторы, которые только смотрят и
выгружают находки) и у модераторов контента (ЦК КС) права одинаковые: нет способа ни
разграничить доступ, ни ответить на вопрос «кто это изменил».

## Решение

Перевести модуль «Лазейки» на ту же идентичность, что и основное приложение —
`get_current_user` из `web/auth.py` (Authentik forward-auth, dev-fallback для локалки) —
и ввести локальную ролевую модель: маппинг `username → role` хранится в БД приложения
(целевое решение; переезд на группы Authentik не планируется). Права проверяются на
каждом эндпоинте модуля.

## Роли и права

| Роль | Определение |
|---|---|
| **Администратор модуля «Лазейки»** | Суперпользователь: все права ЦК КС + `/records/backfill-content` + управление ролями через мини-админку. Запрещено снятие роли последнего администратора |
| **Сотрудник ЦК КС** | Модератор контента: вердикты по лазейкам (с аудитом автора и времени), создание/правка/запуск/остановка парсеров, добавление записей через агента, `/collect/run`, `/refine`, `/clarify` |
| **Пользователь лазеек** (роль по умолчанию) | Read-only: просмотр, скачивание (экспорт PDF/CSV), вопросы агенту по данным; write-инструменты агента для этой роли отключены |

Роль по умолчанию — «пользователь лазеек»: она назначается любому аутентифицированному
пользователю без явной роли. Полный перечень действий — в матрице ниже.

### Матрица «действие → минимальная роль»

| Действие (эндпоинт) | Пользователь | ЦК КС | Админ |
|---|---|---|---|
| Просмотр записей/контента, поиск, ключевые слова, банки, история | ✓ | ✓ | ✓ |
| Экспорт PDF/CSV (скачивание) | ✓ | ✓ | ✓ |
| Чат с агентом — вопросы по данным | ✓ | ✓ | ✓ |
| Чат с агентом — добавление записей | — | ✓ | ✓ |
| Вердикт `is_loophole` (+ аудит changed_by/changed_at) | — | ✓ | ✓ |
| Парсеры: создание, правка, запуск, остановка | — | ✓ | ✓ |
| `/collect/run`, `/refine`, `/clarify` | — | ✓ | ✓ |
| `/records/backfill-content` | — | — | ✓ |
| Управление ролями (мини-админка) | — | — | ✓ |

Функционал **workspaces** (`/workspace`, `/workspaces`) признан легаси и выпиливается
в рамках этой работы.

## Кого это обслуживает

- **Аудиторы Сбера (~50 пользователей)** — потребители данных: смотрят лазейки,
  скачивают выгрузки, спрашивают агента по данным. Успех для них — «открыл и работаю,
  ничего лишнего не сломаю».
- **Сотрудники ЦК КС (5–7 человек, методологи)** — модераторы контента: вердикты по
  находкам, парсеры источников, записи через агента. Успех — полный контроль над
  контентом без риска, что его испортит случайный пользователь.
- **Администратор модуля** — эксплуатация: раздача и смена ролей через админку, без SQL
  и без участия разработчика.

## Критерии успеха

1. Ни одна write-операция модуля не выполняется без требуемой роли (покрыто тестами на эндпоинты).
2. У каждого ручного вердикта есть автор и время изменения (`changed_by` / `changed_at`).
3. Назначение и смена роли делается через админку, без SQL и без участия разработчика.
4. Локальная разработка без Authentik продолжает работать (dev-fallback); продуктовый путь — только через nginx.
5. Выкатка не ломает существующих пользователей: все текущие пользователи модуля стартуют с ролью «пользователь лазеек».

## Scope

### В scope

- Перевод всех эндпоинтов `loophole/web.py` с `X-User-Id` на `get_current_user` (Authentik).
- Локальная ролевая модель: таблица маппинга `username → role` + миграция; первый администратор зашивается миграцией.
- Мини-админка управления ролями (назначение/смена; защита последнего админа).
- Ролевое ограничение эндпоинтов по матрице; отключение write-инструментов агента для роли «пользователь лазеек».
- Аудит ручных вердиктов: `changed_by` / `changed_at`.
- Выпил legacy-функционала workspaces — в том же PR.

### Вне scope

- Основное приложение (чат-аналитик, дайджесты, персонализация) — у него своя идентичность уже есть.
- Переезд ролей на группы Authentik / донастройка форвардинга ОАИТ — не планируется, локальный маппинг является целевым решением.
- Новый workflow-статус лазеек — статусом остаётся существующий вердикт `is_loophole`.

## Vision

При росте аудитории или появлении новых сценариев модель расширяется новыми ролями
и более детальным аудитом действий — без смены подхода.
