# Reconciliation: единый автономный Telegram-парсер

**Change signal:** уточнение пользователя к FR-4 от 2026-08-26.

> Telegram-парсер создаётся единожды как отдельный клиент приложения Telegram вне
> auditLens. В аккаунт добавляются группы/каналы; один автономный парсер ежедневно
> обходит все добавленные цели и сохраняет только новые записи, посты и комментарии.
> Telegram skill позволяет пользователю добавить группу/канал в мониторинг, создав
> соответствующую запись в БД.

## 1. Итог reconciliation

Новый сигнал является более поздним продуктовым решением и **заменяет** текущую
семантику FR-4 «создавать отдельный Telegram-парсер для канала». Целевая семантика:

1. В окружении существует один логический Telegram-клиент/сборщик, а не отдельный
   парсер на каждую цель.
2. Telegram skill не создаёт и не запускает сборщик. Он регистрирует группу или канал
   как цель мониторинга через предназначенную для этого write-операцию в БД.
3. Внешний по отношению к auditLens сборщик работает автономно, ежедневно обходит все
   зарегистрированные и доступные Telegram-аккаунту цели и забирает только новые
   посты, сообщения и комментарии.
4. DB skill остаётся READ-ONLY: запись цели мониторинга выполняется Telegram skill через
   отдельную доменную операцию, а не через произвольный SQL.

Текущие `SPEC.md` и functional brief описывают создание Telegram-парсеров в общем виде
и потому становятся частично устаревшими относительно этого решения. Остальные
решения SPEC о жизненном цикле кейса, верификации и публикации не затрагиваются.

на:

>   Telegram-клиент вне runtime auditLens; его учётные данные и сессия недоступны skill.

### 3.3 Glossary

Добавить определения:

> - **Telegram-сборщик** — один логический автономный клиент Telegram вне runtime
>   auditLens, который по ежедневному расписанию обрабатывает все зарегистрированные
>   цели мониторинга.
> - **Цель мониторинга Telegram** — канонически идентифицированная группа или канал,

>   успешно сохранён для данной Telegram-цели согласно устойчивому идентификатору
>   источника; правило первого запуска определяется OQ-11.

### 3.5 FR-4: целевой текст с сохранением ID

Текущий заголовок оставить: `FR-4. Telegram-parser skill`.

> - **FR-4.1** Skill распознаёт Telegram-цели в поддерживаемых формах (`t.me/...`,
>   `@handle`) и нормализует группу или канал до канонической цели мониторинга.
> - **FR-4.2** По запросу пользователя skill регистрирует группу или канал для
>   мониторинга через предназначенную write-операцию, создающую запись цели в БД;
>   произвольный SQL и DB skill для этой записи не используются.
> - **FR-4.3** Для всех Telegram-целей используется один логический автономный
>   Telegram-клиент вне auditLens; skill не создаёт отдельный парсер, клиент или
>   расписание для каждой цели и не управляет внешним процессом.
> - **FR-4.4** Внешний Telegram-сборщик не реже одного раза в календарный день
>   обрабатывает все активные зарегистрированные цели, доступные его Telegram-аккаунту.
> - **FR-4.5** Каждый цикл сохраняет только новые посты, сообщения и комментарии;
>   повторный запуск и восстановление после сбоя не создают дубликатов уже сохранённых
>   Telegram-записей.
> - **FR-4.6** Повторная регистрация той же канонической цели является идемпотентной:
>   система возвращает существующую активную цель или безопасно восстанавливает её,
>   но не создаёт второй парсер и дублирующую активную регистрацию.

FR-4.4 не утверждает конкретное время запуска: timezone, окно и retry policy остаются
в OQ-12. FR-4.5 не утверждает политику первого backfill: это OQ-11.

Дополнительные acceptance-сценарии для release gate:

1. Новая валидная цель создаёт одну запись мониторинга; skill возвращает её ID и

2. Повтор того же URL/handle не создаёт вторую активную цель.
3. Две разные цели не создают два Telegram-клиента или два per-target расписания.
4. Ежедневный цикл обходит каждую активную доступную цель хотя бы один раз.
5. Повтор цикла с теми же source IDs создаёт ноль дубликатов.
6. После появления новых поста, сообщения и комментария следующий успешный цикл
   сохраняет каждый новый объект ровно один раз.
7. Сбой после частичного сохранения и повторный запуск завершают цикл без потери новых
   объектов и без дублей.
8. Остановка auditLens не останавливает уже настроенное ежедневное выполнение внешнего
   Telegram-сборщика.
9. В auditLens DB и аудит-логах отсутствуют Telegram API credentials и session data.

## 4. Technical mechanisms: изменения `addendum.md`

Следующие пункты описывают реализационную границу и должны находиться в addendum/
архитектуре, а не подменять продуктовые требования FR-4.

### 4.1 Ownership boundary

Добавить в «Решения, вынесенные из PRD»:

> - **Единый Telegram-сборщик** — отдельный от auditLens runtime/сервис владеет одной
>   логической Telegram-сессией и ежедневным scheduler. Он создаётся и настраивается
>   один раз на окружение/аккаунт; добавление новой цели не создаёт новый процесс,
>   клиент или cron job.
> - **Граница Telegram skill** — skill валидирует и нормализует пользовательский ввод
>   и вызывает узкую доменную операцию регистрации цели. Он не получает Telegram
>   credentials/session, не подключается к Telegram и не управляет scheduler.
> - **Граница DB skill** — DB skill остаётся READ-ONLY. Регистрация цели является
>   отдельной allowlisted write-операцией Telegram skill с минимальными правами.
> - **Граница сборщика** — внешний клиент читает активные цели и своё состояние
>   прогресса, получает данные через Telegram API и идемпотентно сохраняет результат.
>   Точная схема, API/очередь и транзакционные границы утверждаются архитектурой.

«Один» следует трактовать как **один логический владелец Telegram-сессии**. Если для
отказоустойчивости допускаются несколько реплик, архитектура обязана обеспечить lease/
leader election, исключающий параллельный активный сбор одной сессией. Это техническое
решение не должно менять FR-4.3.

### 4.2 Логический `TelegramMonitoringTarget v1`

Добавить контракт независимо от физического имени таблицы:

| Группа | Обязательные данные | Семантика |
|---|---|---|
| Идентичность | `target_id`, канонический Telegram peer ID или разрешаемый handle/URL, `target_type=group|channel` | Одна активная регистрация на каноническую цель; URL и handle одной цели не создают дубли |
| Управление | `status`, `created_by`, `created_at`, `updated_at` | Skill создаёт/возвращает регистрацию; правила деактивации пока не определены |
| Доступность | `membership_status` или эквивалент, `last_resolve_error` | Отличает запись в БД от фактической доступности цели Telegram-аккаунту |
| Выполнение | `last_attempt_at`, `last_success_at`, `last_error`, `next_expected_at` | Даёт наблюдаемость ежедневного цикла без доступа к session data |
| Прогресс | устойчивый cursor/high-water mark по цели | Позволяет брать только новые объекты и продолжать после рестарта |
| Аудит | correlation ID регистрации и циклов | Связывает пользовательское действие и автономный сбор без записи секретов |

Физическая модель может разделить target, execution и cursor на несколько таблиц.
PRD требует семантику, но не имя таблицы или конкретный DDL.

### 4.3 Контракт собранного Telegram-объекта

Для дедупликации требуется устойчивый source key, как минимум:

- канонический peer/chat ID;
- Telegram message/post ID;
- для комментария — собственный message ID и ссылка на исходный пост/thread, если
  Telegram API её предоставляет;
- source timestamp, тип объекта и время фактического получения;
- уникальное ограничение/идемпотентный upsert на выбранный source key.

Cursor/high-water mark нельзя продвигать раньше успешного сохранения соответствующего
набора либо до фиксации recoverable checkpoint. Иначе частичный сбой нарушит FR-4.5.
Конкретная стратегия pagination, checkpoint и transaction определяется архитектурой.

### 4.4 Развёртывание, секреты и наблюдаемость

- Telegram API ID/hash, session/string-session и MFA-материалы принадлежат только
  внешнему сервису и его secret store/env; они не входят в БД auditLens.
- Внешний сервис получает отдельную service identity и минимально необходимые права к
  target/cursor/ingestion contract; он не должен получать роль интерактивного аналитика.
- Health/metrics разделяют состояние процесса, Telegram-сессии, каждой цели и каждого
  ежедневного цикла. Ошибка одной цели не должна отменять обработку остальных.
- auditLens показывает или возвращает status регистрации из БД, но не выдаёт успешную
  регистрацию за доказательство успешного Telegram-сбора.

### 4.5 Трассировка и stories

Строку CAP-5 в addendum следует уточнить ссылками `FR-4.1–FR-4.6`, `NFR-2.6–2.7`,
`NFR-4.6`, `NFR-5.3–5.4`, `SM-6.1–SM-6.4` и состоянием:

> **GAP-STORY-03:** нет отдельной story на единственный внешний Telegram-клиент,
> ежедневный incremental-сбор, cursor/idempotency, секреты и автономный deployment.
>
> **GAP-STORY-04:** нет отдельной story на Telegram skill, идемпотентную регистрацию
> цели в БД, контракт target/status и интеграционный тест skill → следующий цикл.

До закрытия GAP-STORY-03/04 нельзя считать FR-4 покрытым Story 1–4/8 только потому,
что существует директория `telegram-parser`.

## 5. Решения пользователя и оставшийся open item

26 августа 2026 года пользователь закрыл продуктовые вопросы reconciliation:

- **OQ-9 — RESOLVED.** Skill только создаёт запись цели в БД; join/subscribe аккаунта
  выполняется другим интерфейсом.
- **OQ-10 — RESOLVED.** Мониторинг сохраняет все доступные новые комментарии, включая
  поздние комментарии к ранее сохранённым постам.
- **OQ-11 — RESOLVED.** При первом успешном обходе собирается вся доступная история.
- **OQ-12 — RESOLVED.** Проверяемая продуктовая граница — хотя бы одна попытка обхода
  каждой активной цели за скользящие 24 часа. Timezone, retry/backoff и точный scheduler
  остаются механизмами архитектуры и не должны ослаблять эту границу.
- **OQ-13.** В какую staging/ingestion-сущность попадают собранные Telegram-объекты и
  как они становятся кейсами AI-исследования/очереди верификации, не обходя FR-11/12?
  **Владелец:** architect/product owner; решить до интеграции внешнего сборщика.

Расширение существующих blockers:

- **BB-1** должен дополнительно требовать архитектурный mapping внешнего процесса,
  service identity, `TelegramMonitoringTarget v1`, cursor/dedupe, ownership Telegram-
  сессии и ingestion boundary.
- **BB-2** должен дополнительно требовать GAP-STORY-03/04 либо эквивалентное явное
  покрытие с приведёнными acceptance checkpoints.

## 6. Разделение «что» и «как»

| Product requirement — должно остаться в PRD | Technical mechanism — должен быть в addendum/architecture |
|---|---|
| Пользователь добавляет группу/канал через skill | Имя таблицы и DTO регистрации |
| Одна каноническая цель не дублируется | Unique index, upsert и canonicalization algorithm |
| Используется один логический внешний Telegram-клиент | Процесс/контейнер, leader lease, библиотека Telegram API |
| Сбор идёт ежедневно по всем активным доступным целям | Cron/scheduler, timezone storage, retry/backoff |
| Сохраняются только новые посты/сообщения/комментарии | Cursor, pagination, checkpoint, transaction и source-key schema |
| Внешний сбор автономен от auditLens | Отдельный deployment/repository, service account, DB/API/queue topology |
| Skill и auditLens не владеют Telegram-секретами | Secret store/env, session format и rotation procedure |
| Результат и ошибки наблюдаемы | Конкретные metrics/log backend, dashboard и alert thresholds |

## 7. Рекомендуемый порядок применения

   `_bmad/scripts/memlog.py`; канонические файлы не редактировать вручную до этого шага.

## 8. Статус reconciliation

- Решения пользователя записаны в `.memlog.md` и применены к `prd.md` и `addendum.md`.
  `SPEC.md` и functional brief этим обновлением не изменялись и требуют последующей

- Уверенность в продуктовой семантике singleton-клиента, initial sync, membership и
