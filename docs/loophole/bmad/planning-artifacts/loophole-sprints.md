# Перечень спринтов: модуль `bank_audit.loophole`

**Основа:** `docs/adr/ADR-001-loophole-refactoring-plan.md`, `docs/adr/ADR-001-loophole-epics-and-stories.md`, `docs/project-analysis.md`, `docs/ARCHITECTURE_LOOPHOLE.md`  
**Дата составления:** 2026-07-27  
**Автор:** John (Product Manager)  
**Контекст ограничений:**
- Фокус: только `bank_audit.loophole`.
- Длительность спринта: 1 неделя.
- Команда: 1 разработчик.
- Горизонт планирования: 30 недель.
- Инфраструктура: без Redis/Celery на старте.
- Приоритет: стабилизация продакшена.

---

## Подход

Каждый спринт — один завершённый инкремент, который можно вмержить в `main` и покрыть тестами.  
Один разработчик, поэтому в спринте не более 2–3 связанных историй.  
Сначала закрываются P0-риски, затем качество кода, затем архитектурная масштабируемость.

| 4.2 | Добавить регрессионные тесты на обходы SQL guard | `pytest tests/loophole/test_db_query_tool.py -q` зелёный |
| 4.3 | Поддержать `LIMIT` (автодобавление или обязательное требование) | Все тесты `tests/loophole` зелёные |

**Результат спринта:** SQL guard надёжен; риск инъекций/обходов снижен.

## Sprint 5 — Безопасность: heal с human-in-the-loop, часть 1

**Цель:** перестать применять патчи автоматически; ввести модель pending-патча.

| История | Что делаем | Критерий приёмки |

| 5.1 | Отключить автоматическое применение патча в `heal_tick`/`_heal_worker` | Heal формирует `patch_proposal`, но не пишет в файл без одобрения |

| 5.3 | Добавить API `GET /parsers/{id}/pending-patch` | Возвращает список предложенных патчей; покрыто тестами |

**Результат спринта:** автоматический heal больше не меняет код; появляется аудит-точка.

## Sprint 6 — Безопасность: heal с human-in-the-loop, часть 2

## Риски и рекомендации

1. **Один разработчик + 1 неделя.** Если история не укладывается — дробить дальше. Не увеличивать scope спринта.
2. **Нет Redis/Celery.** Sprint 10 (async backfill) реализован внутри процесса. При росте нагрузки или необходимости отдельного worker-процесса — вернуться к вопросу Redis/ARQ.
3. **Greenplum 6.** Все SQL-изменения (batch insert, FTS) должны проверяться на реальном диалекте, а не только на SQLite.
4. **Линтер как gate.** Сначала придётся снизить существующие 120 ошибок ruff — иначе CI будет красным с первого PR.
5. **Human-in-the-loop heal.** Требует UI-изменений; если фронтовая часть отстаёт, сделать API и минимальный UI, а полировку отложить.
