Целевая архитектура модуля «Уязвимости»

Материал для утверждения владельцами продукта. Это TO-BE дизайн: миграции, RBAC, worker и runtime evidence пока UNVERIFIED.

Кандидат не появляется в каталоге до положительного решения эксперта. Повтор публикации безопасен и не создаёт дубль.

2. Telegram отделён от приложения

Один внешне развёрнутый worker владеет Telegram-сессией, обходом и checkpoint. Fail-closed sanitizer либо создаёт masked ingress object, либо карантинирует только метаданные без persistence body и LLM. AuditLens создаёт revisioned evidence, а аналитик явно выбирает его для исследования. Прямая публикация запрещена.

Telegram
→
Внешний worker
→
Masked ingress
→
Evidence
→
Явное исследование

Для каждой активной цели attempt начинается не реже одного раза в 24 часа. Global session lease, target fence, versioned source key и checkpoint обеспечивают один обход и безопасный failover. При деактивации registry сам закрывает попытку и создаёт audit relay; при crash это делает ограниченный reaper. Stale worker только останавливается.

4. Контроль качества и безопасности

OIDC JWT идентифицирует subject, а workspace membership и role assignment перепроверяются в БД до любой команды. Все mutating действия имеют actor, run_id, payload-bound idempotency key и immutable evidence snapshot. agent_audit_log хранится 14 дней и читается только администратором; worker journal, inbox/outbox и dead-letter сохраняют exactly-once audit delivery в отдельный 30-day horizon. DB skill остаётся read-only.

5. Условия запуска

До запуска требуются UX-маршруты для исследования и очереди, DCL allow/deny для пяти database principals, OIDC verification, worker perimeter, fencing/reaper/revoke tests, sanitizer/quarantine tests, 24-hour SLO и parity tests перед удалением legacy shim.
