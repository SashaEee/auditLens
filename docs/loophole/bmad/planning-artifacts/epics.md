# auditLens — декомпозиция на эпики и истории

## Обзор

Документ фиксирует извлечённые требования для реализации модуля «Уязвимости». Целевая архитектура имеет статус TO-BE: её runtime-реализация, миграции, DCL/RBAC и внешний Telegram worker пока **UNVERIFIED**. Эпики и истории будут проектироваться только в следующих шагах workflow.

### Дополнительные требования архитектуры

- Реализация — модульный монолит с гексагональными границами; Telegram — отдельный deployment без FastAPI transport, прямой записи таблиц и доступа к research/catalog/verification/audit-log.
- Агент использует только шесть allowlisted skills, лимит 20, `AgentFactory`, SSE и redacted аудит с retention 14 дней.
- Доменные владельцы разделены: Research, Verification, Publication, Catalog, SourceEvidence, Target registry/access и IngestionAuditProjector; direct SQL write запрещён.
- Ввести `CaseContract v1`, `ReportFilter v1`, `ScheduledQueryContract v1`, immutable `submitted_case_revision`, `CommandLedger v1`, `CaseFingerprint v1` и state machines исследования, верификации и публикации.
- Положительное решение создаёт idempotent `publication_pending`; единственный `publication_mapping` и повтор с тем же command key не допускают дублей; fuzzy merge запрещён.
- OIDC Principal проверяется по pinned issuer/audience/JWKS; membership и capability перепроверяются сервером на каждом endpoint/tool/scheduled run; авторизация fail-closed.
- Роль ЦК КС назначает `module_admin`, не более пяти активных экспертов; административный доступ и аудит изолированы.
- DB skill принимает только parsed single-statement `SELECT` против allowlisted views через `loophole_readonly`; scheduled query не содержит raw SQL, результат private, TTL ≤24 ч, без automatic external export.
- Ввести идемпотентные SQL-миграции 042 lifecycle, 043 Telegram ingestion и 044 audit/security с DDL/DCL, unique constraints и SECURITY DEFINER controlled functions.
- Telegram target имеет global canonical identity, alias index, provisional-to-canonical resolver merge, workspace subscription и отдельные registry/access операции; redirect ID блокируется.
- Worker владеет одним `telegram_session_id`, leases, generation-fencing, durable initial checkpoint, initial/incremental сбором, structured attempt journal, outbox/inbox и 24-hour SLO.
- До persistence/LLM применять versioned fail-closed sanitizer: хранить только redacted ingress/evidence и keyed HMAC; full raw body/replacement map не сохранять; uncertain/unsupported payload — metadata-only quarantine.
- Evidence выбирается и submit-ится только с active workspace subscription; snapshot pin-ит grant version. Revoke блокирует новые выбор/submit, но не уже accepted snapshot, решение и обязательную публикацию.
- Отдельные principals и least privilege обязательны: `auditlens_app`, `loophole_readonly`, `telegram_worker`, `ingestion_reaper`, `audit_retention`, schema owner; нужны PostgreSQL allow/deny acceptance и staging evidence для OIDC, DCL, leases, PII, deployment, secret/CA/firewall.

### UX-требования

- **UX-DR-1:** реплицировать токены сайта 1:1 в iframe (`:root`/`html.dark`), убрать локальные hex/ad-hoc radii/shadows; использовать тёплую paper-систему, Geist/Source Serif 4/JetBrains Mono, один accent и русский UI.
- **UX-DR-2:** синхронизировать `html.dark` iframe с родителем через `MutationObserver`; при прямом открытии применять `prefers-color-scheme`; проверить все поверхности обеих тем.
- **UX-DR-3:** использовать только self-hosted vendor-ресурсы; не применять `100vh`/корневой `overflow:hidden`; считать breakpoints от ширины iframe.
- **UX-DR-4:** реализовать ширины `>=1400`, `1100–1399`, `736–1099`, `<736`; на 1280×720/iframe ≈992×600 header доступен, page-level horizontal scroll отсутствует, таблица/очередь скроллятся только внутри.
- **UX-DR-5:** дать отдельные маршруты каталога, AI-исследования, очереди ЦК КС и admin-поверхности; не рендерить недоступные пункты и при прямом URL применять fail-closed экран без данных в DOM.
- **UX-DR-6:** показывать чат только в AI-исследовании: docked справа на ширинах >=1100, off-canvas 320–380px ниже 1100 с overlay, Escape, focus-trap, возвратом фокуса, сохранением сообщений/черновика/операции и кнопкой повторного открытия.
- **UX-DR-7:** реализовать header с переносом действий, фильтры с debounce 300–400ms и единым `STATUS_OPTIONS`, доступную сортировку `aria-sort`, строковые details, checkbox-only selection и массовую панель без перекрытия последней строки.
- **UX-DR-8:** различать loading/error/empty/offline состояния; у каждой ошибки давать понятное действие «Повторить»; показывать один toast info/success/error и не использовать `alert()`/`confirm()`.
- **UX-DR-9:** реализовать доступные модалки и off-canvas: семантические контролы, `:focus-visible`, role/dialog/aria-modal/labelledby, Escape, focus-trap и возврат фокуса; поддержать reduced motion.
- **UX-DR-10:** обеспечить контраст ≥4.5:1, текст ≥11px, мишени ≥28px, текстовые статусы помимо цвета, отсутствие emoji/технических ID, локализованный прогресс SSE.
- **UX-DR-11:** UI исследования должен поддерживать явный выбор разрешённого evidence, неизменяемый submitted snapshot, статус «Ожидает решения» и невозможность ранней публикации.
- **UX-DR-12:** UI очереди показывает pending snapshot, источники, обязательный комментарий и три текстово обозначенных решения; конкурентное решение показывает сохранённый итог; публикация имеет видимые состояния и идемпотентный retry.
- **UX-DR-13:** административный маршрут ограничить назначением/отзывом ЦК КС, статусом мониторинга и сводным аудитом; отзыв роли в активной сессии очищает очередь и показывает fail-closed экран.

## Список эпиков

### Эпик 1: Контролируемое рабочее пространство модуля

Аналитик, эксперт ЦК КС и администратор безопасно входят в релевантный им рабочий контекст, который адаптируется к iframe и соответствует дизайн-системе AuditLens.

**FRs covered:** FR-9.1—FR-9.7, FR-10.1—FR-10.4.

**Заметки реализации:** серверная fail-closed авторизация является источником истины; UI не смешивает каталог, исследование, очередь и администрирование. Эпик даёт общую доступную UI-оболочку и защищённые маршруты для следующих эпиков.

### Эпик 2: Изолированное AI-исследование лазеек

Аналитик задаёт вопрос агенту, видит локализованный ход исследования, кейсы и разрешённые источники, классифицирует и экспортирует результат без преждевленной публикации в каталог.

**FRs covered:** FR-1.1—FR-1.5, FR-2.1—FR-2.4, FR-7.1—FR-7.6, FR-8.1—FR-8.2, FR-11.1—FR-11.4.

**Заметки реализации:** ReAct ограничен allowlisted skills и аудитом; результаты принадлежат изолированному research-контексту. Эпик зависит от защищённых маршрутов эпика 1, но не от будущего Telegram ingestion.

### Эпик 3: Проверка ЦК КС и надёжная публикация

Эксперт изучает immutable submitted snapshot и источники, принимает единственное решение, а положительный кейс автоматически и идемпотентно появляется в общей базе.

**FRs covered:** FR-12.1—FR-12.5.

**Заметки реализации:** Verification и Publication services разделены; нужны state machine, immutable snapshot, command ledger, `CaseFingerprint v1`, повтор публикации и аудит. Эпик использует исследования эпика 2.

### Эпик 4: Каталог, аналитика и экспорт

Аналитик находит опубликованные кейсы, выполняет безопасную аналитику и получает XLSX, CSV или PDF с единым набором фильтров и понятными ограничениями.

**FRs covered:** FR-5.1—FR-5.3, FR-6.1—FR-6.6.

**Заметки реализации:** каталог показывает только published confirmed cases; DB skill использует read-only allowlisted views, а scheduled results остаются private и ограниченными TTL. Эпик использует опубликованные данные эпика 3.

### Эпик 5: Обычные источники и управляемые парсеры

Аналитик создаёт, запускает, наблюдает и планирует парсеры нетелеграм-источников без смешения с Telegram-контуром.

**FRs covered:** FR-3.1—FR-3.5.

**Заметки реализации:** создание и выполнение парсеров остаётся отдельным риск-контуром; Telegram-парсеры запрещены. Эпик поставляется после каталога и экспорта, поскольку его ценность не блокирует основную аналитическую работу.

### Эпик 6: Безопасный Telegram-мониторинг

Аналитик регистрирует Telegram-цель, а независимый worker с единственной сессией регулярно собирает только безопасно обезличенные ingress-объекты с checkpoint и без дублей.

**FRs covered:** FR-4.1—FR-4.9.

**Заметки реализации:** worker отделён от AuditLens, владеет leases/fencing и 24-hour SLO; TargetRegistry и TargetAccess разделены; raw payload не сохраняется и не попадает в LLM. Эпик опирается на identity/RBAC эпика 1, но не требует парсеров.

## Эпик 1: Контролируемое рабочее пространство модуля

Аналитик, эксперт ЦК КС и администратор безопасно входят в релевантный им рабочий контекст, который адаптируется к iframe и соответствует дизайн-системе AuditLens.

### Story 1.1: Авторизованный выбор рабочего контекста

Как внутренний пользователь,
я хочу видеть только доступные мне рабочие контексты модуля,
чтобы не получать доступ к данным или действиям вне моей роли.

**Критерии приёмки:**

**Дано** пользователь открывает модуль,
**Когда** сервер подтверждает его principal, membership и capabilities,
**Тогда** UI показывает «Общую базу» и «Новое AI-исследование», а «Очередь верификации» — только при роли ЦК КС.
**И** каждый запрос к защищённому контексту повторно проверяет авторизацию на сервере.

**Дано** пользователь без роли ЦК КС открывает прямой URL очереди,
**Когда** сервер отклоняет запрос,
**Тогда** UI показывает fail-closed экран «Нет доступа к очереди верификации» с действием возврата.
**И** данные очереди, карточки кейса и источники отсутствуют в DOM.

**Дано** роль ЦК КС отозвана во время активной сессии,
**Когда** пользователь выполняет следующий запрос к очереди,
**Тогда** UI очищает ранее загруженные данные и показывает тот же fail-closed экран.

### Story 1.2: Единая оболочка iframe и синхронизация темы

Как внутренний пользователь,
я хочу видеть модуль в единой с AuditLens визуальной системе,
чтобы работа в iframe воспринималась как часть основного продукта и оставалась читаемой в обеих темах.

**Критерии приёмки:**

**Дано** модуль открыт внутри same-origin iframe,
**Когда** загружается его интерфейс,
**Тогда** он использует только саморазмещённые React, ReactDOM, Babel и шрифты из `/static/vendor/`.
**И** внешние CDN и локальные hex-палитры не используются.

**Дано** основной сайт переключает `html.dark`,
**Когда** изменяется класс родительского документа,
**Тогда** iframe синхронно применяет или снимает `html.dark` через `MutationObserver`.
**И** при прямом открытии iframe тема выбирается через `prefers-color-scheme`.

**Дано** модуль отображает таблицу, чат, модалку или toast,
**Когда** пользователь переключает тему,
**Тогда** все поверхности используют единые токены AuditLens и сохраняют контраст текста не ниже 4.5:1.

### Story 1.3: Адаптивные маршруты рабочих контекстов

Как внутренний пользователь,
я хочу работать с каталогом, AI-исследованием и очередью верификации на отдельном адаптивном экране,
чтобы данные и действия разных стадий не смешивались.

**Критерии приёмки:**

**Дано** пользователь выбирает рабочий контекст,
**Когда** открывается его маршрут,
**Тогда** на экране показаны только относящиеся к нему данные и действия.
**И** каталог, AI-исследование и очередь ЦК КС не совмещаются на одной рабочей поверхности.

**Дано** iframe имеет ширину 1280×720-эквивалента (около 992×600),
**Когда** отображается заголовок и основные действия,
**Тогда** кнопки остаются доступны через перенос на вторую строку.
**И** у страницы отсутствует горизонтальная прокрутка.

**Дано** iframe сужается ниже 1100px,
**Когда** таблица или очередь не помещается по ширине,
**Тогда** второстепенные колонки скрываются по приоритету, а URL доступен в деталях строки.
**И** горизонтальная прокрутка разрешена только контейнеру таблицы или очереди.

### Story 1.4: Доступные состояния и обратная связь интерфейса

Как внутренний пользователь,
я хочу получать понятную обратную связь от каждого рабочего экрана,
чтобы отличать загрузку, отсутствие данных и ошибку и безопасно управлять действиями с клавиатуры.

**Критерии приёмки:**

**Дано** экран запрашивает данные,
**Когда** запрос выполняется, завершается пустым результатом или ошибкой,
**Тогда** UI показывает три разные поверхности: загрузку, пустой результат с действием «Сбросить» и ошибку с действием «Повторить».
**И** ошибка не маскируется под пустой результат.

**Дано** действие пользователя успешно выполнено или завершилось ошибкой,
**Когда** UI сообщает результат,
**Тогда** он показывает один toast соответствующего типа: информационный, успешный или ошибочный.
**И** деструктивное действие требует модального подтверждения с описанием последствия, а `alert()` и `confirm()` не используются.

**Дано** пользователь управляет модалкой или off-canvas панелью клавиатурой,
**Когда** он открывает и закрывает её,
**Тогда** фокус остаётся внутри активного слоя, Escape закрывает его, а затем фокус возвращается на открывший контрол.
**И** все интерактивные элементы семантические, имеют видимый `:focus-visible`, мишени не меньше 28px и русские подписи.

### Story 1.5: Администрирование роли ЦК КС и сводного аудита

Как администратор модуля,
я хочу назначать и отзывать роль ЦК КС и просматривать сводный аудит,
чтобы управлять доступом к верификации без раскрытия рабочих данных.

**Критерии приёмки:**

**Дано** пользователь имеет активную роль `module_admin`,
**Когда** он назначает или отзывает роль ЦК КС,
**Тогда** сервер проверяет capability и сохраняет аудитируемое изменение роли.
**И** одновременно активны не более пяти экспертов ЦК КС.

**Дано** администратор открывает административный маршрут,
**Когда** его права подтверждены,
**Тогда** он видит только управление ролями, статус Telegram-целей и сводный redacted аудит.
**И** черновики исследований, очередь, каталог и технические payload не смешиваются с этой поверхностью.

**Дано** пользователь без административного права открывает прямой URL,
**Когда** сервер отклоняет запрос,
**Тогда** UI показывает fail-closed экран без деталей отказа и без данных в DOM.

## Эпик 2: Изолированное AI-исследование лазеек

Аналитик задаёт вопрос агенту, видит локализованный ход исследования, кейсы и разрешённые источники, классифицирует и экспортирует результат без преждевленной публикации в каталог.

### Story 2.1: Управляемый агент исследования

Как аналитик,
я хочу запустить изолированное исследование через управляемого агента,
чтобы получать полезный ответ без неограниченных действий или записи в общий каталог.

**Критерии приёмки:**

**Дано** аналитик создаёт новое AI-исследование,
**Когда** он отправляет запрос в области поддерживаемых умений,
**Тогда** агент выполняет ReAct-цикл через `AgentFactory` и `SkillRegistry` с allowlisted skills.
**И** максимальное число итераций по умолчанию равно 20 и настраивается без изменения кода.

**Дано** запрос неполный или неоднозначный,
**Когда** агент не может безопасно продолжить,
**Тогда** он показывает уточняющий вопрос и ожидает ответ аналитика.
**И** ожидание ответа не расходует итерацию.

**Дано** достигнут лимит итераций либо один skill вернул некритичную ошибку,
**Когда** агент завершает цикл,
**Тогда** аналитик получает лучший доступный или частичный ответ с понятным объяснением.
**И** ошибка одного skill не приводит к неявному сбою всего исследования.

**Дано** агент выполнил шаги исследования,
**Когда** запуск завершается,
**Тогда** в redacted `agent_audit_log` сохранены пользователь, запрос, инструменты, длительность, результат и `run_id`.
**И** пользователь видит список применённых инструментов без технических аргументов и секретов.

### Story 2.2: Поиск источников и извлечение кейсов

Как аналитик,
я хочу получить из веб-источников структурированные потенциальные кейсы с первоисточниками,
чтобы оценивать обнаруженные лазейки на основе проверяемого материала.

**Критерии приёмки:**

**Дано** аналитик задал тему исследования,
**Когда** агент выполняет web-поиск и загружает выбранные URL,
**Тогда** он сохраняет для результата исследования параметры запроса, использованные источники и извлечённый текст.
**И** каждый кейс содержит ссылку на первоисточник.

**Дано** прочитан текст источника,
**Когда** агент извлекает потенциальную лазейку,
**Тогда** он создаёт структурированный кандидат по `CaseContract v1`.
**И** кандидат сохраняется только в контексте текущего AI-исследования.

**Дано** источник недоступен или извлечение текста завершилось ошибкой,
**Когда** агент продолжает исследование,
**Тогда** аналитик получает понятное сообщение об ограничении источника.
**И** агент не создаёт фиктивный кейс и не прекращает весь запуск, если доступны другие источники.

**Дано** кейсы извлечены,
**Когда** исследование завершено,
**Тогда** ни один непроверенный кандидат не появляется в общей базе.
**И** аналитик может просмотреть связь каждого кандидата с его источниками.

### Story 2.3: Модельная классификация результатов исследования

Как аналитик,
я хочу получить модельную оценку каждого найденного кейса,
чтобы быстрее отобрать материалы для дальнейшей проверки, не теряя ручной контроль.

**Критерии приёмки:**

**Дано** исследование содержит один кейс или фильтрованную выборку,
**Когда** аналитик либо агент запускает классификацию,
**Тогда** classifier определяет для каждого кандидата признак `is_loophole`, уровень уверенности и обоснование.
**И** модель и размер внутренних пакетов берутся из конфигурации.

**Дано** агент завершает web-исследование,
**Когда** извлечены кандидаты,
**Тогда** они проходят модельную классификацию до показа итогового результата.
**И** классификация использует подтверждённые примеры и профильный prompt.

**Дано** у кейса уже есть ручной verdict аналитика или решение ЦК КС,
**Когда** выполняется classifier,
**Тогда** он не изменяет ни одно из этих значений.
**И** модельная оценка хранится отдельно и остаётся прослеживаемой.

**Дано** classifier не смог обработать часть выборки,
**Когда** операция завершается,
**Тогда** пользователь видит, какие записи не получили модельный verdict и почему.
**И** успешно обработанные записи сохраняют свои результаты.

### Story 2.4: Наблюдаемый и адаптивный ход исследования

Как аналитик,
я хочу видеть ход AI-исследования и управлять панелью агента без потери контекста,
чтобы продолжать работу на любом поддерживаемом размере iframe.

**Критерии приёмки:**

**Дано** аналитик запускает типовое исследование,
**Когда** агент приступает к работе,
**Тогда** первый локализованный промежуточный статус появляется не позднее 15 секунд.
**И** фазы отображаются понятными подписями: «Уточнение», «Выполнение», «Ответ», без технических ID.

**Дано** ширина iframe не меньше 1100px,
**Когда** открыт экран AI-исследования,
**Тогда** панель агента закреплена справа от результатов и может быть скрыта пользователем.
**И** после скрытия результаты занимают освободившееся место, а кнопка повторного открытия остаётся доступна.

**Дано** ширина iframe от 736 до 1099px,
**Когда** аналитик выбирает «Открыть чат»,
**Тогда** открывается правая off-canvas панель шириной 320–380px с затемнением.
**И** Escape, клик по затемнению и кнопка закрытия закрывают панель, возвращая фокус на кнопку открытия.

**Дано** панель чата закрыта во время или после исследования,
**Когда** аналитик открывает её снова,
**Тогда** сообщения, черновик ввода и ход операции сохраняются.
**И** закрытие панели не отменяет запущенное исследование.

### Story 2.5: Передача выбранного кейса на верификацию

Как аналитик,
я хочу явно выбрать кейс и разрешённые источники для передачи в очередь ЦК КС,
чтобы эксперт рассматривал точный и неизменяемый материал.

**Критерии приёмки:**

**Дано** исследование содержит кандидаты и связанные источники,
**Когда** аналитик выбирает кейс для верификации,
**Тогда** UI показывает понятное резюме кейса, его первоисточники и текущую версию.
**И** разрешается выбрать только evidence с активным доступом workspace.

**Дано** аналитик подтверждает отправку,
**Когда** система создаёт submitted snapshot,
**Тогда** она сохраняет неизменяемую версию кейса, выбранные revisions evidence, автора, время и correlation `run_id`.
**И** одна и та же версия кейса не создаёт второй submitted snapshot.

**Дано** submitted snapshot создан,
**Когда** аналитик изменяет исходный черновик исследования,
**Тогда** изменённый черновик не подменяет отправленный материал.
**И** UI показывает статус «Ожидает решения ЦК КС».

**Дано** доступ к выбранному evidence отозван до отправки,
**Когда** аналитик пытается передать кейс,
**Тогда** операция отклоняется без раскрытия недоступных метаданных.
**И** UI предлагает вернуться к явному выбору разрешённых источников.

## Эпик 3: Проверка ЦК КС и надёжная публикация

Эксперт изучает immutable submitted snapshot и источники, принимает единственное решение, а положительный кейс автоматически и идемпотентно появляется в общей базе.

### Story 3.1: Рассмотрение кейса и единственное решение ЦК КС

Как эксперт ЦК КС,
я хочу рассмотреть переданный неизменяемый кейс и принять одно решение с комментарием,
чтобы верификация была прослеживаемой и не допускала противоречивых итогов.

**Критерии приёмки:**

**Дано** эксперт с действующей ролью ЦК КС открывает очередь,
**Когда** он выбирает pending-кейс,
**Тогда** он видит только submitted snapshot, закреплённые источники и provenance.
**И** черновик исследования или изменения после отправки не подменяют материал.

**Дано** эксперт вводит обязательный комментарий,
**Когда** он выбирает «Уязвимость», «Мошенническая схема» или «Не подтверждено»,
**Тогда** система сохраняет решение, эксперта, время, комментарий и `run_id`.
**И** запись решения append-only и связана с submitted snapshot.

**Дано** два эксперта почти одновременно принимают решение по одному snapshot,
**Когда** первый запрос фиксирует итог,
**Тогда** второй запрос получает уже сохранённое решение без создания нового решения или побочного эффекта.
**И** UI показывает зафиксированный итог вместо локального ложного успеха.

**Дано** пользователь без роли ЦК КС пытается прочитать или принять решение,
**Когда** сервер проверяет запрос,
**Тогда** он отклоняет его fail-closed.
**И** ни snapshot, ни источники, ни детали очереди не раскрываются.

### Story 3.2: Идемпотентная публикация подтверждённого кейса

Как аналитик и эксперт ЦК КС,
я хочу, чтобы положительно подтверждённый кейс публиковался в общей базе ровно один раз,
чтобы каталог оставался достоверным даже при повторных попытках и сбоях.

**Критерии приёмки:**

**Дано** эксперт сохранил решение «Уязвимость» или «Мошенническая схема»,
**Когда** Verification service фиксирует итог,
**Тогда** Publication service создаёт состояние «Публикуется» с тем же idempotency command key.
**И** каталог получает кейс только после успешной публикации.

**Дано** положительное решение повторно обрабатывается или публикация перезапускается,
**Когда** Publication service получает тот же command key,
**Тогда** он возвращает ранее созданный результат либо продолжает тот же процесс публикации.
**И** в каталоге не создаётся второй кейс или второй `publication_mapping`.

**Дано** публикация временно завершилась ошибкой,
**Когда** пользователь или сервис выполняет допустимый повтор,
**Тогда** UI последовательно показывает «Публикуется», «Не удалось опубликовать» или «Опубликовано».
**И** повтор доступен только в состоянии ошибки и не меняет решение ЦК КС.

**Дано** эксперт сохранил «Не подтверждено»,
**Когда** решение становится окончательным,
**Тогда** Publication service не создаёт публикацию.
**И** в аудит записываются решение и отсутствие публикации с общим `run_id`.

### Story 3.3: Миграции и ограничения жизненного цикла кейса

Как владелец продукта,
я хочу, чтобы lifecycle исследования, верификации и публикации был закреплён миграциями и ограничениями БД,
чтобы некорректный переход или повторная операция не могли обойти доменные правила.

**Критерии приёмки:**

**Дано** начинается развёртывание lifecycle-функций,
**Когда** применяются новые SQL-миграции,
**Тогда** они идут следующими номерами после существующих миграций, идемпотентны и создают только нужные сущности lifecycle, unique constraints и controlled functions.
**И** миграции содержат DDL/DCL, необходимые для границ доменных сервисов.

**Дано** система создаёт submitted snapshot, финальное решение или publication mapping,
**Когда** операция повторяется или конкурирует с другой операцией,
**Тогда** constraints гарантируют одну submitted-версию, одно финальное решение и одну publication mapping для нужного ключа.
**И** сервис возвращает уже сохранённый результат либо typed ошибку, а не создаёт дубликат.

**Дано** staging PostgreSQL доступен,
**Когда** выполняются acceptance-проверки lifecycle,
**Тогда** подтверждаются конкурентные решения, сбой/повтор публикации и запрет ранней публикации.
**И** при отсутствии staging эти проверки помечаются UNVERIFIED, а не успешными.

## Эпик 4: Каталог, аналитика и экспорт

Аналитик находит опубликованные кейсы, выполняет безопасную аналитику и получает XLSX, CSV или PDF с единым набором фильтров и понятными ограничениями.

### Story 4.1: Поиск и фильтрация опубликованного каталога

Как аналитик,
я хочу отобрать опубликованные кейсы по единым фильтрам и просмотреть их детали,
чтобы быстро находить нужные подтверждённые материалы.

**Критерии приёмки:**

**Дано** аналитик открывает общую базу,
**Когда** система загружает каталог,
**Тогда** она возвращает только published confirmed cases, доступные пользователю.
**И** результаты AI-исследований и pending-кейсы не отображаются.

**Дано** аналитик изменяет банк, период, текстовый поиск, признак лазейки, тип кейса или статус верификации,
**Когда** применяется фильтр,
**Тогда** таблица и все дальнейшие экспорты используют один `ReportFilter v1`.
**И** текстовый поиск имеет debounce 300–400ms, а «Сбросить» возвращает исходное состояние.

**Дано** аналитик работает с таблицей,
**Когда** он сортирует, выбирает или открывает строку,
**Тогда** сортировка доступна с клавиатуры и передаёт `aria-sort`, чекбокс изменяет только выделение, а строка или отдельная кнопка открывает детали.
**И** смысл статусов передаётся текстом, а не только цветом.

### Story 4.2: Экспорт отфильтрованных данных

Как аналитик,
я хочу выгрузить отобранные данные в подходящем формате,
чтобы передать проверяемый результат стейкхолдерам без ручной обработки.

**Критерии приёмки:**

**Дано** аналитик задал фильтры каталога,
**Когда** он выбирает XLSX, CSV или PDF,
**Тогда** экспорт использует тот же `ReportFilter v1`, что и таблица.
**И** файл содержит только опубликованные доступные записи.

**Дано** аналитик экспортирует результат AI-исследования,
**Когда** формируется файл,
**Тогда** он содержит кейсы, первоисточники и параметры исходного запроса.
**И** непроверенные материалы не выдаются за опубликованный каталог.

**Дано** XLSX-выборка превышает 10 000 записей,
**Когда** аналитик запускает экспорт,
**Тогда** система не создаёт неполный файл.
**И** UI сообщает фактическое число записей и предлагает сузить фильтры.

**Дано** PDF-экспорт недоступен из-за Playwright или браузера,
**Когда** система обрабатывает запрос,
**Тогда** она возвращает явную структурированную ошибку.
**И** UI предлагает повторить запрос или выбрать XLSX/CSV.

### Story 4.3: Безопасная аналитика опубликованного каталога

Как аналитик,
я хочу выполнять разрешённые аналитические запросы к каталогу,
чтобы получать дополнительные срезы данных без риска изменить их или обойти ограничения доступа.

**Критерии приёмки:**

**Дано** аналитик запускает DB skill,
**Когда** он передаёт запрос,
**Тогда** система принимает только один разобранный оператор `SELECT` к allowlisted views через роль `loophole_readonly`.
**И** параметры передаются отдельно от текста запроса.

**Дано** запрос содержит DML, DDL, несколько операторов, неразрешённую таблицу или функцию,
**Когда** DB skill валидирует запрос,
**Тогда** выполнение блокируется до обращения к БД.
**И** аналитик получает понятное объяснение допустимой формы запроса.

**Дано** разрешённый запрос выполняется успешно,
**Когда** получен результат,
**Тогда** он возвращается как JSON-таблица, пригодная для отображения в интерфейсе.
**И** применяются timeout и жёсткий лимит строк.

### Story 4.4: Управляемое расписание аналитических запросов

Как аналитик,
я хочу включать и отключать разрешённую аналитическую задачу по расписанию,
чтобы получать внутренний результат без хранения или запуска произвольного SQL.

**Критерии приёмки:**

**Дано** аналитик выбирает доступную именованную аналитическую задачу,
**Когда** он включает расписание,
**Тогда** система сохраняет `ScheduledQueryContract v1` с идентификатором и версией запроса, workspace, владельцем, получателем и сроком действия.
**И** raw SQL не сохраняется в контракте.

**Дано** наступает время запуска,
**Когда** scheduler проверяет контракт,
**Тогда** он выполняет задачу только при действующем членстве владельца и получателя, нужных capabilities и неистёкшем сроке.
**И** иначе создаётся одно аудит-событие `schedule_skipped_<причина>` без выполнения запроса.

**Дано** задача успешно завершена,
**Когда** формируется `ScheduledResult v1`,
**Тогда** результат остаётся во внутреннем приватном назначении workspace с ACL владельца и получателя.
**И** TTL не превышает 24 часов, а внешний адресат и автоматический экспорт запрещены.

## Эпик 5: Обычные источники и управляемые парсеры

Аналитик создаёт, запускает, наблюдает и планирует парсеры нетелеграм-источников без смешения с Telegram-контуром.

### Story 5.1: Создание валидируемого парсера обычного источника

Как аналитик,
я хочу создать парсер обычного веб-источника по описанию,
чтобы регулярно получать данные без повторного ручного поиска.

**Критерии приёмки:**

**Дано** аналитик описывает обычный источник и ожидаемые данные,
**Когда** система создаёт парсер,
**Тогда** она сохраняет его в изолированном каталоге с идентификатором, конфигурацией и проверяемым статусом.
**И** создание Telegram-парсера отклоняется с объяснением, что Telegram обслуживается отдельным контуром.

**Дано** созданный парсер не проходит валидацию,
**Когда** проверка завершается,
**Тогда** аналитик видит понятный результат и журнал проверки.
**И** невалидный парсер не становится доступен для расписания.

### Story 5.2: Запуск и наблюдение обычного парсера

Как аналитик,
я хочу запустить созданный парсер и наблюдать его состояние,
чтобы понимать результат и причину сбоя без доступа к инфраструктуре.

**Критерии приёмки:**

**Дано** доступный валидный парсер,
**Когда** аналитик запускает его по требованию,
**Тогда** система создаёт отдельный run со статусом и журналом выполнения.
**И** UI показывает переходы «Запущен», «Завершён» или «Ошибка» без молчаливого сбоя.

**Дано** run завершился ошибкой,
**Когда** аналитик открывает его статус,
**Тогда** он видит безопасное объяснение и действие повтора, если повтор допустим.
**И** ошибка одного run не изменяет конфигурацию парсера и не затрагивает другие runs.

### Story 5.3: Расписание и управление жизненным циклом обычного парсера

Как аналитик,
я хочу включать и отключать расписание валидного парсера,
чтобы контролировать регулярный сбор данных.

**Критерии приёмки:**

**Дано** парсер валиден,
**Когда** аналитик включает или отключает его расписание,
**Тогда** изменение сохраняется отдельно для этого парсера и аудитируется.
**И** отключённый парсер не запускает новые плановые runs.

**Дано** плановый run начинается,
**Когда** scheduler запускает парсер,
**Тогда** его статус и журнал доступны через тот же интерфейс, что и ручного run.
**И** расписание не создаёт Telegram-клиент, Telegram-сессию или Telegram-цель.

## Эпик 6: Безопасный Telegram-мониторинг

Аналитик регистрирует Telegram-цель, а независимый worker с единственной сессией регулярно собирает только безопасно обезличенные ingress-объекты с checkpoint и без дублей.

### Story 6.1: Идемпотентная регистрация Telegram-цели

Как аналитик,
я хочу зарегистрировать Telegram-группу или канал для мониторинга,
чтобы независимый сервис мог начать проверять его доступность и сбор.

**Критерии приёмки:**

**Дано** аналитик передаёт `t.me/...`, `@handle` или допустимую invite-ссылку,
**Когда** Telegram skill обрабатывает команду,
**Тогда** `TargetRegistryService` нормализует адрес и идемпотентно создаёт либо возвращает цель.
**И** повторная команда не создаёт дубликат и не изменяет произвольные записи.

**Дано** цель зарегистрирована,
**Когда** система возвращает результат,
**Тогда** она явно различает регистрацию цели, доступность аккаунту и успешный сбор.
**И** skill не вступает в группу, не управляет membership, сессией или worker.

### Story 6.2: Управление доступом и жизненным циклом Telegram-цели

Как администратор модуля,
я хочу отдельно выдавать доступ workspace и активировать или деактивировать цель,
чтобы контролировать, кто может использовать evidence и когда worker выполняет сбор.

**Критерии приёмки:**

**Дано** active `module_admin` имеет capability `target_subscription_manage`,
**Когда** он выдаёт или отзывает workspace subscription,
**Тогда** `TargetAccessService` изменяет только canonical target и аудитирует субъект, время и результат.
**И** redirect ID, другой workspace и отсутствие capability отклоняются fail-closed.

**Дано** администратор деактивирует цель,
**Когда** операция фиксируется,
**Тогда** новые обходы не начинаются, активная попытка завершается с fenced terminal event, а история и checkpoint не удаляются.
**И** после повторной активации worker продолжает корректный initial или incremental путь.

### Story 6.3: Независимый безопасный Telegram ingestion

Как аналитик,
я хочу, чтобы активная доступная цель собиралась независимым сервисом без дублей,
чтобы использовать новые сообщения и комментарии как безопасный источник для исследования.

**Критерии приёмки:**

**Дано** активная canonical Telegram-цель доступна worker,
**Когда** выполняется её первый успешный обход,
**Тогда** внешний worker сохраняет всю доступную историю постов, сообщений и комментариев как ingress-объекты.
**И** worker не создаёт research, candidate, verification request или каталог.

**Дано** initial sync завершён,
**Когда** worker выполняет следующий обход,
**Тогда** он сохраняет только новые объекты и поздние комментарии после устойчивого checkpoint.
**И** identity/version и дедупликация не допускают повторное сохранение объекта.

**Дано** worker получает текст или вложение,
**Когда** sanitizer не может уверенно одобрить его,
**Тогда** он fail-closed помещает объект только в metadata-only quarantine.
**И** полный raw body, replacement map и вложения не попадают в persistence, LLM или audit.

### Story 6.4: Устойчивый Telegram worker и наблюдаемый SLO

Как владелец сервиса,
я хочу, чтобы один логический worker устойчиво обслуживал Telegram-цели и сообщал о сбоях,
чтобы ни отказ экземпляра, ни повторная попытка не создавали параллельную сессию или потерю данных.

**Критерии приёмки:**

**Дано** имеется несколько экземпляров worker,
**Когда** они пытаются начать работу,
**Тогда** только владелец global session lease и target lease с актуальным fencing token выполняет обход.
**И** stale worker не может записать batch или checkpoint.

**Дано** worker аварийно завершился до или после первого batch,
**Когда** lease истекает,
**Тогда** `ingestion_reaper` terminalize-ит незавершённую попытку и сохраняет единственный outbox/audit summary.
**И** новый владелец продолжает с последнего устойчивого checkpoint без дублей.

**Дано** цель активна или повторно активирована,
**Когда** контролируется сервисный уровень,
**Тогда** первая попытка и каждый следующий `attempt_started` укладываются в скользящее окно 24 часов либо цель находится в единственном незавершённом обходе.
**И** структурированный журнал содержит режим синхронизации, checkpoint до/после, счётчики, длительность и безопасную ошибку.

### Story 6.5: Защищённый perimeter и доказательства готовности worker

Как владелец платформы,
я хочу развернуть Telegram worker с отдельными правами и проверить его perimeter,
чтобы внешний ingestion не мог получить доступ к данным или действиям AuditLens вне своей роли.

**Критерии приёмки:**

**Дано** развёрнуты runtime principals,
**Когда** применяются DCL и controlled functions,
**Тогда** `auditlens_app`, `loophole_readonly`, `telegram_worker`, `ingestion_reaper` и `audit_retention` имеют только минимально необходимые права.
**И** worker не имеет прямой записи таблиц, доступа к каталогу/research/verification/`agent_audit_log` или DCL.

**Дано** worker запущен в production-like окружении,
**Когда** проверяется его perimeter,
**Тогда** он является отдельным deployment без inbound HTTP listener, использует отдельный service account, TLS/CA validation и secrets только из approved secret manager.
**И** его egress ограничен Telegram и managed PostgreSQL.

**Дано** готовится release candidate,
**Когда** выполняются staging-проверки,
**Тогда** есть доказательства allow/deny для principals, OIDC отказов, lease/fencing, PII sanitation, cleanup, secret rotation, firewall и alert ownership.
**И** отсутствие внешней проверки фиксируется как UNVERIFIED.
