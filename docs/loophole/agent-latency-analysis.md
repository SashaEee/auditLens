## Подтверждённые причины

1. **Медленные последовательные обращения к модели.** Runtime checkpoint показывает
   `google/gemini-2.5-flash`. В текущей конфигурации `LOOPHOLE_NANOBOT_MODEL` отсутствует,
   поэтому модель выбирается из `LLM_MODEL_FAST`:
   [config.py:93](/F:/auditLens/src/bank_audit/loophole/config.py:93).
   Упоминание GPT-4.1 в проектной инструкции не описывает этот фактический запуск.
   Механика цикла: ответ модели → инструменты → следующий ответ модели. Замеры выше
   подтверждают длительность этой фазы, но не доказывают, что причина внутри Gemini,
   а не в обслуживающем её провайдере или сети. Ошибки retry на этих трёх интервалах
   не наблюдались.

2. **Основной поиск настроен на адрес Docker из процесса Windows.** Реальные getters
   конфигурации в свежем процессе возвращают `SEARXNG_URL=http://searxng:8080`.
   `socket.getaddrinfo('searxng')` на этом хосте даёт `gaierror 11001` за 2277,3 мс.
   Контейнер `auditlens-searxng` работает, порт 8888 опубликован на хост;
   `GET http://127.0.0.1:8888/` возвращает 200 за 290,5 мс. Это проверка доступности
   веб-сервиса, а не качества его поисковой выдачи. В живом запуске каждый показанный
   поиск заканчивает попытку SearXNG ошибкой `ConnectError` и переходит на DDGS.
   Там наблюдаются таймауты, Google 429 и повторные попытки. Два поиска на третьей
   итерации завершились около 20:20:12 и 20:20:30, четыре на шестой заняли 29,35 с.

3. **Инструменты блокируют асинхронный цикл.** `async execute` вызывает синхронные
   функции напрямую: [tools_nanobot.py:654](/F:/auditLens/src/bank_audit/loophole/chat/tools_nanobot.py:654),
   [tools_nanobot.py:685](/F:/auditLens/src/bank_audit/loophole/chat/tools_nanobot.py:685).
   Даже при `gather` поиски фактически последовательны. Offline-проверка настоящих
   обёрток с искусственной задержкой 100 мс: три вызова занимают 301–302 мс,
   heartbeat не выполняется весь этот промежуток; `wait_for(timeout=20ms)`
   не прерывает блокирующий вызов и возвращается после 100 мс.
   Это воспроизведение дефекта механики, не измерение реальной сети.
   [Скрипт](/F:/auditLens/workspace/qa/latency-tools-20260907/offline_probe.py),
   [результаты](/F:/auditLens/workspace/qa/latency-tools-20260907/offline_probe.json).

4. **«Найди 1» не ограничивает объём исследования.** Системный prompt требует
   нескольких кластеров, разных площадок и продолжения широкого поиска:
   [07_nanobot_system.md:70](/F:/auditLens/src/bank_audit/loophole/chat/prompt/07_nanobot_system.md:70).
   Есть обязательное разложение на 2–4 схемы и повторный поиск при нерелевантной
   выдаче (:98, :106), но нет явного условия завершения после одной подтверждённой
   находки. В шестой итерации агент снова запустил четыре поисковых запроса.
   Это объясняет расширение работы; оно не означает, что нужная находка уже была
   подтверждена и агент намеренно проигнорировал готовый результат.

5. **Лимит итераций не ограничивает общее время.** Дефолт — 20 циклов:
   [config.py:10](/F:/auditLens/src/bank_audit/loophole/config.py:10).
   Общего deadline в [ManagedAgent](/F:/auditLens/src/bank_audit/loophole/agent/__init__.py:142)
   нет. Установленная библиотека nanobot-ai 0.2.2 не применяет внешний wall-clock
   timeout к streaming-вызову; HTTP timeout 120 с и stream-idle timeout 90 с
   не ограничивают весь запуск. После исчерпания итераций возможен отдельный
   финализирующий LLM-вызов. Встроенные повторы nanobot остаются, несмотря на
   отключённые SDK retries. Для этого запуска их вклад не подтверждён.

6. **Интерфейс получает текст только после окончания работы.** Дельты складываются
   в буфер ради полного redaction:
   [graph.py:588](/F:/auditLens/src/bank_audit/loophole/chat/graph.py:588),
   [hooks.py:31](/F:/auditLens/src/bank_audit/loophole/chat/hooks.py:31).
   Это усиливает ощущение зависания. Безопасную обработку ПД при оптимизации
   необходимо сохранить.

## Что не подтверждено как причина этого запуска

- Clarification: точная строка пользователя проходит детерминированно без LLM
  (`actionable_product_period_scope`), проверено offline с запрещённым вызовом клиента.
- Большая прежняя переписка: в workspace 37 было только одно пользовательское сообщение.
  Контекст вырос уже внутри поиска: журнал показывает 12 859 → 18 328 входных токенов.
- Медленная БД: соединение и чтение количества сообщений заняли 152,9 мс при первом
  подключении, затем 2,0 и 1,7 мс. Это узкий замер, не профиль всех SQL-запросов.
- Общий отказ сервера: во время ожидания модели `/healthz` ответил 200 за 22,6 мс.
  Это не исключает блокировки сервера именно во время синхронных инструментов.
- RAG/эмбеддинги: не входят в allowlist исследованного runtime-пути.
- Дополнительная LLM внутри `audit_extract_loopholes`, отсутствие явного timeout
  у её клиента и ошибочный вызов Playwright Sync API из async-контекста выявлены
  отдельно. Их вклад в измеренные итерации не установлен; найденные проблемы
  нельзя автоматически считать причиной именно этих интервалов.

## Рекомендуемые изменения и проверка эффекта

1. Для запуска на Windows выставить адрес SearXNG `http://127.0.0.1:8888`, затем
   проверить реальный поиск. Для контейнерного запуска сохранить Docker-адрес.
2. Добавить общий бюджет времени и бюджет по этапам. Считать запрос «1 лазейка»
   отдельным ограничением: завершать после одной проверенной находки; при отсутствии
   доказательств возвращать честный частичный результат по истечении бюджета.
3. Перевести сетевые search/fetch на async I/O либо вынести блокирующий I/O в поток;
   ограничить параллельность независимых чтений. Назначение `asyncio.to_thread`
   описано в [официальной документации Python](https://docs.python.org/3/library/asyncio-task.html#asyncio.to_thread).
   SQLAlchemy Session нельзя совместно использовать между такими потоками;
   изменение БД и общего контекста оставлять под контролем владельца сессии.
4. Явно закрепить модель агента и измерить её задержку на одном и том же запросе.
   Не приписывать весь интервал до инструментов вычислениям модели. Добавить
   тайминги provider/first chunk/final chunk/tool и число повторов.
5. Сохранить маскирование ПД и показывать проверенные этапы прогресса; улучшение
   отображения не подменяет сокращение фактического времени.

При последующей реализации сравнивать одинаковый запрос по общему времени,
количеству LLM/search/fetch, времени каждого этапа и наличию одного подтверждённого
результата. Подтверждение требует прочитанного источника, соответствия 2026 году
и сохранения доказательств. Короткое время само по себе не является успехом.
