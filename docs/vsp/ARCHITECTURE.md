# Сборщик отзывов о ВСП: архитектура

Независимый модуль `bank_audit.vsp` (каталог `src/bank_audit/vsp/`). Он собирает, хранит и обновляет публичные отзывы о территориальных подразделениях Сбербанка (ВСП) из 2ГИС и Яндекс Карт. Модуль никак не подключён к приложению AuditLens:

- его не импортируют ни веб-приложение, ни планировщик;
- у него своя база (`VSP_DB_URL`) и свои таблицы `vsp_*`;
- запускается он отдельной командой `python -m bank_audit.vsp …`.

## Схема

```
                ┌──────────────── реестр отделений ────────────────┐
  Банк России   │ registry/cbr.py   9 997 подразделений, адреса     │
  (JSON-страница│ registry/match.py ключ адреса, здание, без склейки │
   cbr.ru)      │ registry/apply.py привязка карточек к реестру     │
                └───────────────┬───────────────────────────────────┘
                                │ vsp_branch ←→ vsp_source_branch
   ┌──────────────┬─────────────┴──────┬──────────────────┐
   │ TwoGisCollector │ YandexMapsCollector │ DomclickCollector │   collectors/*
   │ public_api      │ page_state | api    │ (заглушка)        │   единый интерфейс
   └───────┬──────────┴──────────┬──────────┴──────────────────┘   Collector
           │  SourceHttp: частота, повторы, распознавание блокировки (http.py)
           ▼                     ▼
   sync.py: проход отделения → страницы → storage.save_reviews → прогресс
            полнота по факту, пропавшие отзывы, режимы full / new
           ▼
   storage.py: vsp_review, vsp_review_version, vsp_sync_state, vsp_sync_run, vsp_sync_error
           ▼
   report.py: отчёт о полноте (Markdown), выгрузка JSONL
```

## Единый интерфейс адаптера (`collectors/base.py`)

| Метод | Что делает |
|---|---|
| `discover(area)` | Находит отделения Сбербанка в городе или рядом с точкой и возвращает их карточки без отзывов. |
| `branch(id)` | Отдаёт карточку отделения: адрес, координаты, заявленное число отзывов и рейтинг. Если карточки нет, бросает `NotFound`. |
| `pages(id, sort, cursor)` | Отдаёт страницы отзывов от курсора до конца выдачи источника. |
| `capabilities` | Честно описывает ограничения источника: метод, сортировки, есть ли полная история, потолок выдачи. |

Частота запросов, повторы, прогресс, дедупликация и расчёт полноты общие для всех адаптеров. Адаптер их не реализует.

## Источники

| Источник | Метод | Полнота | Пагинация и сортировка |
|---|---|---|---|
| **2ГИС** | Публичный сервис отзывов, который использует сам 2gis.ru. Ключ — из настроек страницы. | Вся история отзывов с текстом (заявлено = получено). Оценки без текста видны только числом. | `offset` по 50; сортировки `date_edited`, `date_created`, `friends`. |
| **Яндекс Карты, по умолчанию** | Данные страницы организации, обычный HTTP. | До 600 на отделение. Небольшие отделения собираются целиком, у крупных — около трети. | Страницы 1–12 по 50, порядок по релевантности. |
| **Яндекс Карты, `VSP_YANDEX_SIGNED_API=1`** | Внутренний сервис отзывов с подписью запроса, как в коде страницы. | Объединение четырёх сортировок по 600 (замер: 1 318 из 1 944, 68%). | `by_time` для «только новых»; `union` для полного прохода. |
| **Домклик** | — | Отзывов об отделениях нет (только о риелторах). Сайт закрыт JS-проверкой Qrator. | — |

Поиск отделений:
- **2ГИС.** Страницы поиска `/{город}/search/СберБанк/page/N`, по 12 объектов: id, адрес, координаты, организация, число отзывов. Банкоматы — отдельные организации, отбрасываются. Каталог 2ГИС подписан, подпись не воспроизводится.
- **Яндекс.** Страница сети `/maps/213/moscow/chain/sberbank/6003612/?ll=…&z=16`: до 10–15 ближайших отделений. Префикс региона обязателен, иначе 404; выдачу определяет `ll`. Точками служат координаты реестра или карточек 2ГИС.
- **Ежедневная дельта 2ГИС (следующий шаг, ещё не реализован).** Лента отзывов организации `/3.0/orgs/{orgId}/reviews?sort_by=date_edited` — проверено 05.11. Она отдаёт новые отзывы всех отделений организации одним потоком, у каждого отзыва есть `object.id` отделения, курсор — `offset_date`. Параметр `fields` для организаций не принимается (400). Один запрос на организацию вместо одного на каждое отделение.

## Реестр и сопоставление

- **Основа реестра — Банк России.** Список ВСП: 9 540 дополнительных офисов, 447 передвижных пунктов кассовых операций, 10 прочих точек. В нём есть код ВСП («8602/0112»), номер подразделения (`FILIAL_NUM`), адрес и дата открытия; координат нет. Около 300 доп. офисов — кассово-инкассаторские центры без клиентов: статус `cash_center`, к ним карточки по адресу не привязываются.
- **Ключ адреса.** `город|улица|дом[к корпус][с строение]`. Он сводит форматы ЦБ («Г. АБАКАН, УЛ. ПУШКИНА, Д. 165, СТРОЕНИЕ 1»), 2ГИС («Пушкина, 165 ст1») и Яндекса («Россия, Абакан, улица Пушкина, 165с1»).
- **Правила привязки** (`registry/apply.py`):
  0. Карточка Яндекса с номером подразделения ЦБ (`nomer_sp_cbr`) привязывается по нему к отделению с тем же `FILIAL_NUM`. Это точная привязка, `registry_code`. Условие — по реестру это стационарный офис в том же городе. Иначе (передвижной пункт, КИЦ, другой город) — конфликт на разбор.
  1. Карточка источника привязывается к отделению реестра, если ключ адреса совпал ровно с одним отделением. Если с двумя и больше — это конфликт, без привязки.
  2. Иначе карточка привязывается через карточку другого источника в том же здании: взаимно-лучшая пара в пределах 60 м, или до 250 м при том же доме.
  3. Иначе карточка остаётся без привязки и попадает в отчёт.
- **Отделения одного источника не объединяются никогда.** По одному названию — тоже никогда.

## Синхронизация (`sync.py`)

- **`full`.** Полный проход с начала до конца выдачи. Он обновляет ответы банка, записывает правки в историю (`vsp_review_version`) и помечает пропавшие отзывы (`gone_at`, без удаления). У источника с потолком пропавшим считается только отзыв внутри достижимого окна дат.
- **`new`.** Выдача «сначала новые» по дате правки. Остановка — на первой странице, где всё известно, без правок **и** старше прошлой успешной синхронизации минус 3 дня. Одного «всё знакомо» мало: отзыв, отредактированный без смены текста, поднимается выше новых. Без прошлой успешной синхронизации `new` идёт до конца выдачи. У Яндекса без подписи выдача по релевантности, поэтому `new` там равен короткому полному проходу (до 12 страниц).
- **«Получено» — разные отзывы за проход**, не строки страниц: выдача по релевантности повторяет отзывы на соседних страницах. Число повторов пишется в журнал.
- **Продолжение.** После каждой страницы сохраняются курсор и начало прохода. Прерванный проход продолжается с курсора, а пропавшие отзывы определяются верно.
- **Блокировка.** Капча, 401 или 403 вызывают `SourceBlocked`. Источник останавливается до конца прогона, причина пишется в состояние и журнал ошибок. Капчу сборщик не решает, прокси не меняет.
- **Временные сбои.** Сеть, 429 и 5xx повторяются с растущей паузой. При исчерпании повторов проход отделения получает статус `partial`, а остальные продолжают.
- **Полнота по факту:**
  - `complete` — получено не меньше заявленного (допуск 2%);
  - `below_declared` — источник заявляет больше, чем отдаёт;
  - `window` — упёрлись в потолок выдачи;
  - `partial` — проход прерван;
  - `blocked` — источник ограничил доступ.

## Дописывание и демон (`mass.py`)

Первичная загрузка и дописывание устроены одинаково. У новой карточки нет состояния, значит, ей пора полный проход. После любого прохода `sync.schedule_next` ставит две даты:
- **`next_due_at`** — следующая проверка «только новых». Интервал выбирается так, чтобы к проверке ожидался примерно один новый отзыв по частоте за 90 дней, в пределах 6–48 часов: активные отделения — до четырёх раз в день, тихие — раз в двое суток.
- **`next_full_at`** — полный проход раз в 30 дней с постоянным сдвигом до трёх суток, чтобы проходы не сбивались в один день.

`Store.due` отдаёт, кому пора. После сбоя отделение ждёт повтора 6 часов, а не крутится в цикле. Отсутствующие и закрытые карточки проверяются только по `next_full_at`.

Демон — три цикла в одном процессе:
- **обслуживание:** реестр ЦБ раз в сутки, поиск отделений раз в месяц с продолжением после остановки, привязка каждые 6 часов;
- **сбор 2ГИС;**
- **сбор Яндекса.**

Ограничение частоты общее на хост внутри процесса (`http.host_limiter`): поиск и сбор одного хоста вместе не превышают заданную частоту.

Блокировка источника (капча, 401/403) ставит паузу на 3 часа и снижает частоту в 0,7 раза. Частота хранится в базе, `vsp_kv`.

| Действие | Запросов на отделение |
|---|---|
| 2ГИС, проверка «только новых» | 1 (карточка и первая страница — один ответ) |
| Яндекс с подписью, проверка «только новых» | 1 JSON-запрос: сессия со страницы одной организации годится для любых других, страница грузится раз в 20 минут |
| Яндекс с подписью, полный проход | 1 + ⌈N/50⌉ при N ≤ 600; объединение сортировок — только у отделений больше 600 отзывов, и останавливается, когда собрано заявленное |
| Яндекс без подписи, любой проход | до 12 страниц (порядок по релевантности, «только новые» невозможны) |

Сопоставление на всей сети работает по сетке координат: соседние ячейки ≈ 250 м. 9 тыс. × 9 тыс. карточек обрабатываются за доли секунды, результат совпадает с полным перебором.

## Форматы офисов

СберПервый, Private Banking, обслуживание юрлиц и бизнеса, исламский офис, круглосуточная зона, головной офис ГОСБ, передвижной пункт. Формат сводится в `vsp_branch.formats` с источниками (`registry/apply.apply_formats`):

| Источник | Что даёт |
|---|---|
| Сайт банка (`registry/banksite.py`) | Флаги форматов, часы работы, услуги по каждому офису; код ВСП в названии — точная привязка к реестру (замер 05.11: 7 382 из 7 387 стационарных офисов, плюс 3 270 остановок на 390 маршрутах передвижных офисов) |
| Яндекс | `office_type` (`office_vip`, `office_sme`, `office_corporate`, `office_retail`), `devision_type_bank` (`branch_bank` — головной офис) |
| 2ГИС | Карточки СберПервого внутри организации банка и отдельная организация Private Banking — **дочерние** к ВСП своего здания: в паре «2ГИС — Яндекс» не участвуют, привязываются к основной карточке того же адреса (`parent_card`) |
| Реестр ЦБ | Передвижные пункты, кассово-инкассаторские центры |

## Сигналы вкладки (`signals/`)

Расчёт идёт ночью раз в сутки (01–06 МСК) внутри демона, в отдельном потоке. Можно запустить и вручную: `python -m bank_audit.vsp signals`. На 155 тыс. отзывов уходит около 17 секунд.

- **«Похоже на кампанию отзывов»** (`campaign.py`).
  - Что считаем: неподтверждённые пятёрки в окне 14 дней.
  - Ожидание точки: её доля в потоке клиентов группы (1–4★ и подтверждённые пятёрки за 24 месяца), умноженная на пятёрки остальной группы в том же окне. Группа — ГОСБ.
  - Рост по всей сети или по всему ГОСБ поднимает ожидание сам. Поэтому точка выделяется, только если она выше своей группы.
  - Пороги окна: 10+ пятёрок, кратность ≥ 3, p ≤ 10⁻⁶.
  - Подкрепления дают балл 0–100: разовые авторы, пачки до 10 минут, конец месяца, шаблоны, пометки площадки, волна жалоб перед эпизодом. Доля подтверждённых балл снижает.
- **Синхронный всплеск ГОСБ** — то же на ступень выше: ГОСБ против сети. Балл умножается на охват (сколько ВСП ГОСБ участвует).
- **Авторы** (`authors.py`): шкала автора (знаток города / рассыльщик жалобы / постоянный клиент / хвалебщик сети), кольца (3+ автора с 3+ общими ВСП в пределах 30 дней), один текст в разных ВСП. Отзывы Flamp в признаки авторов не идут.
- **Сеть** (`network.py`): календарь по месяцам, события из данных, ответы банка, нормы признаков по годам.
- **Витрина** (`run.py`):
  - балл отбора и причины по каждой точке;
  - агрегаты для карты: доля ВСП в фокусе по субъекту и ГОСБ, «значимо выше сети» при z ≥ 2,58.
- **Проверка «балл ≠ объём»** (ρ Спирмена ≤ 0,5): считается по точкам с 30+ отзывами за год, где сигнал применим.
  - Точки с меньше чем 10 отзывами в год помечены «мало данных».
  - Замер 05.11: по всем точкам ρ = 0,51, у точек с 30+ отзывами — 0,11, со 100+ — 0,02.

## Чтение отзывов моделью (`signals/llm_read.py`)

Возможные нарушения в отделениях находит не список фраз, а модель. Она читает отзывы в три этапа:

1. **Отбор** (`--stage screen`). Есть ли в отзыве конкретный эпизод для проверки отделения. Модель — `openai/gpt-oss-120b`.
2. **Карточка** (`--stage card`) — только по отобранным отзывам. Модель — `deepseek-ai/DeepSeek-V4.1-Flash`. В карточке:
   - что произошло;
   - действия сотрудника и какой контроль нарушен;
   - продукт, роль, уязвимость клиента, сумма;
   - чья вина: сотрудник, отделение, политика банка;
   - серьёзность 0–3;
   - дословная цитата. Код проверяет, что она действительно есть в тексте.
3. **Уточнение** (`--stage detail`) — только тяжёлые истории (серьёзность 2–3) с 2021 года. Модель — та же, что у карточки. Поля:
   - тип истории — один из 25 (`signals/kinds.py`): что именно сделали с клиентом;
   - короткое описание способа своими словами (из него потом собираются «почерки»);
   - кому выгода, по словам клиента: план продаж, сотрудник лично, третьи лица;
   - что сделал сотрудник: ошибка, ввёл в заблуждение, действовал за клиента или присвоил;
   - пишет ли клиент, что случай не единичный; чем закончилось; куда обращался;
   - произошло ли это в этом отделении; если нет — какое отделение назвал клиент;
   - окно, вид суммы (потеря или размер продукта), дата события.
   Стоит ≈0,25 ₽ за историю, поэтому старые истории не уточняются: тип им ставит код по действиям карточки (`risk.kind_from_actions`).

Уже прочитанное отсеивает база, поэтому шаг дешёвый и идёт каждый час внутри демона (см. «Чтение как шаг сборщика»).

Одинаковые тексты читаются один раз. Массовые аккаунты пропускаются: 40 и больше отзывов о банке у одного аккаунта — это политическая рассылка или рассылка одной жалобы. Расход держится ниже лимита Cloud.ru: 100 тыс. токенов в минуту на модель (`VSP_LLM_TPM`). Траты считаются в рублях, есть потолок (`VSP_LLM_CAP_RUB`).

## Что считается массовым: клиенты, почерки, волны, очаги, полки

Замер 10.11 на 775 тыс. отзывов: число тяжёлых историй по отделениям распределено почти как случайное
(отделений с 2+ клиентами за 2 года — 391, чистая случайность при тех же объёмах даёт 378). Поэтому
балла отделения нет. Массовое ищем на уровне «способ действия × территория × время».

- **Один клиент — один раз** (`signals/clients.py`). Внутри отделения склеиваются: один автор на одной площадке; близкий текст в пределах полутора месяцев (копия на 2ГИС и Яндексе); почти тот же текст в любое время. Один текст на карточках нескольких отделений в волнах и очагах считается один раз (`dup_of`).
- **Где случилось.** Если клиент пишет о другом отделении и называет его код, история переносится туда; если не называет — помечается «не здесь» и в счёт отделения не идёт. Карточка центрального офиса (`VSP_HQ_CODES`) собирает жалобы на банк в целом и в сравнении отделений не участвует.
- **Почерки** (`signals/motifs.py`, команда `motifs`). Модель-редактор читает короткие описания способа внутри каждого типа и предлагает каталог узких приёмов — название, описание, чем это может объясняться безобидно, какие операции запросить и какой показатель снимет вопрос. Работает в три шага: предлагает каталог типа по выборке описаний; раскладывает каждое описание по каталогу; из того, что не подошло, один раз предлагает ещё несколько почерков и раскладывает остаток. Новые почерки предлагаются только отдельным вызовом по всему остатку — иначе параллельные пачки придумывают одно и то же разными словами. В каталоге типа не больше 16 почерков, остальное — «прочее» типа. Типы разбираются одновременно через одного клиента модели (общий счёт токенов в минуту). Новые описания следующих ночей относятся к каталогу; приём, который повторился, становится новым почерком. Закрытого списка нет. Таблицы `vsp_motif`, `vsp_motif_label`.
- **Экспозиция** (`signals/stats.py`). Знаменатель — отзывы, которые прочитала модель, по месяцам и ячейкам «площадка × жалоба или нет». Состав отзывов меняется (в 2026 году на 2ГИС в разы выросло число положительных), и без ячеек свежие волны выглядели бы затухающими.
- **Волны** (`signals/waves.py`). Для каждого типа и почерка — клиенты по месяцам и состояние: «новое» (почти всё появилось за год), «растёт» (за три месяца или за год значимо чаще прежнего — точное сравнение двух периодов с поправкой на число сравнений), «затихает», «ушло», «идёт давно». Считается с даты, с которой тип ставит модель. Типы и почерки проверяются отдельными семьями с общим бюджетом ложных находок (типам 0,8, почеркам 0,2 — `stats.bh_levels`): одной семьёй сотня мелких рядов почерков делала поправку для типов в разы строже, и «растёт» у типов пропадало.
- **Очаги** (`signals/hotspots.py`). Способ действия у трёх и больше клиентов в двух и больше отделениях одного города или ГОСБ за 9 или 18 месяцев либо за всё время. Проверка: сколько из всех случаев сети за то же окно пришлось бы на территорию при ровном распределении (биномиальная, по ячейкам); вероятность умножается на число окон; затем поправка Бенджамини — Хохберга: «сильный» очаг — доля ложных 5 %, «слабый» — 20 % (бюджет так же делится между типами и почерками). Если очаг найден по типу, а большинство его клиентов (от 60 %) описывают один почерк, очаг получает «главный почерк» — это пояснение, а не отдельная проверка; по нему строится запрос данных. Тест `test_uniform_background_rarely_gives_strong_hotspots` проверяет долю ложных на ровном фоне.
- **Полки отделений** (`signals/risk.py`):
  - «выделяются наверняка» — клиентов с тяжёлыми историями за 2 года или 5 лет значимо больше ожидаемого по прочитанным отзывам (поправка на число отделений); полка часто пуста, и это честный результат;
  - «виден один почерк» — три и больше клиента за год описывают один способ, и столько не могло набраться случайно при частоте остальной сети за тот же год. Поправка — на все пары «отделение × способ», где есть хоть одна история (а не только на те, где набралось три: так на перемешанных данных прода на полку попадало 1–12 отделений при 19 настоящих; теперь — 0,2 при 4). Сюда же вывод модели по отделению, если названные ею истории проходят ту же проверку: три клиента за год, плюс поправка на то, что модель сама выбирает, какие типы объединить (число наборов типов у отделения). Сам по себе вывод модели на полку не ставит: модель почти всегда отвечает «общий почерк есть» (11.11 — 424 отделения из 594). Тест `test_uniform_background_rarely_fills_branch_shelves`;
  - отдельные тяжёлые случаи — очередь историй за год по важности: сначала поступок сотрудника (действие за клиента, личная выгода), потом сумма и обстоятельства.
- **Вывод по отделению** (`signals/branch_llm.py`, команда `branch-read`). Модель читает все тяжёлые истории отделения разом (по одной на клиента) и отвечает, есть ли общий почерк, какие истории к нему относятся, что известно об исполнителях, чем это может объясняться безобидно и что запросить. Число клиентов, период и значимость считает код. Перечитывается, только когда состав историй изменился. Таблица `vsp_branch_llm`.
- **Запрос данных.** У каждого типа и почерка есть «что запросить» и «какой показатель снимет вопрос»; вкладка собирает из них готовый текст для отделения, очага или способа действия и выгружает в Word.

### Чтение как шаг сборщика

Раньше новые отзывы читал внешний цикл рядом с демоном. Теперь это шаг обслуживания (`mass._analysis`):

- каждый час — отбор, карточка и уточнение новых отзывов, с дневным потолком трат `VSP_LLM_DAILY_RUB` (по умолчанию 300 ₽);
- ночью — почерки → расчёт → выводы по отделениям → расчёт с выводами;
- **сторож** (`watch.py`): если подходящие отзывы ждут чтения дольше суток (`VSP_LLM_STALE_H`), демон пишет в журнал, а вкладка показывает плашку «модель отстаёт с чтением». Состояние — в `status` и в `/api/vsp/meta`.

Шаг работает, когда демону доступны `LLM_BASE_URL` и `LLM_API_KEY`; выключается `VSP_LLM_ENABLED=0`.

## Вкладка «Аудит сети ВСП» в приложении (`web/vsp_api.py`, раздел `vsp`)

- **Доступ.** Список логинов `VSP_USERS`; если он пуст — только владелец (`ADMIN_USERS`). Остальным раздел в меню не показывается, сервер отвечает 403.
- **База.** Вкладка только читает базу сборщика (`SET SESSION CHARACTERISTICS AS TRANSACTION READ ONLY`). Адрес — `VSP_DB_URL`; если он не задан, берётся адрес основной базы приложения с базой `VSP_DB_NAME` (по умолчанию `vsp_reviews`) и схемой `VSP_DB_SCHEMA` (`vsp`).
- **Кэш.** Последний расчёт держится в памяти 5 минут.
- **API** `/api/vsp/*`:
  - вкладка: `meta`, `brief`, `waves`, `waves/{id}`, `hotspots`, `hotspots/{id}`, `map?key=`, `home?shelf=`, `queue`, `dossier/{point}`, `stories`, `table`, `evidence/{rid}`, `search`, `feedback`;
  - выгрузки: `export/justification.xlsx`, `export/stories.xlsx`, `export/visit.docx`, `export/request.docx`, `export/candidates.xlsx`, `export/reviews.xlsx`;
  - прежние экраны про волны пятёрок: `overview`, `signals`, `signals/{id}`, `branches`, `branches/{point}`, `reviews`, `links`, `groups/{id}`, `completeness`.
- **Колокольчик.** Когда способ действия становится «новым» или «растёт», тем, кому открыт раздел, приходит строка в колокольчик (`vsp_wave`); письмом она не дублируется. Первый раз — только владельцу и не больше трёх строк. О способе, который уже был «новым» или «растёт», повторно не сообщается 45 дней (`WAVE_MEMORY_D`): ряд на границе значимости иначе слал бы одну и ту же строку каждые несколько дней. Что уже сообщали — `app_setting`, ключ `vsp_waves_seen`.
- **Имена сотрудников** в текстах показываются как есть. `vsp/names.py` нужен только для фильтра «упомянут сотрудник». Между ВСП имена не сопоставляются.
- **Интерфейс** — `VspPage` в `app.jsx`, стили `.vsp` и `.vr` в `index.html`. Разделы:
  - «Главное» — за пять минут: что идёт по сети → где сгущается → кого смотреть → что запросить;
  - «Схемы» — способы действия по кварталам с состоянием и список очагов;
  - «Где проверить» — карта «больше ожидаемого» (по всем историям или по одному способу), ГОСБ, три полки, таблица отделений;
  - «Истории» — все истории с фильтрами и вид «Изнутри»;
  - слои со своим адресом: случай, досье отделения, способ действия, очаг, план проверки, «Как это работает».

## Режимы запуска

| Режим | Команда |
|---|---|
| Одно отделение | `sync --source 2gis --id <id>` |
| Город или регион | `sync --source 2gis --city Казань` / `--region …` |
| Все регионы (только по согласованию) | `sync --source 2gis --all --i-know-this-is-mass` |
| Только новые отзывы | `sync … --mode new` |
| Обновить существующую базу | `sync … --mode full` |
| Поиск отделений | `discover --source 2gis --city …` |
| Привязка к реестру | `match` |
| Отчёт о полноте и выгрузка | `report --out …` / `export --out …` |
| Пилот | `pilot` (продолжить с шага Яндекса — `pilot --from-step yandex`) |
| Вся сеть по расписанию (сбор + дописывание) | `daemon --i-know-this-is-mass` |
| Реестр ЦБ / обход всей сети | `registry` / `discover-all --source 2gis\|yandex` |
| Сводка: карточки, полнота, кому пора, паузы, сторож чтения | `status` |
| Чтение отзывов моделью | `llm-read --stage screen\|card\|detail\|both\|all [--cap-rub N]` |
| Почерки / расчёт вкладки / выводы по отделениям | `motifs` / `signals` / `branch-read` |
| Вся ночная цепочка одним запуском | `nightly [--cap-rub N]` |
| Паспорт ВСП с сайта банка | `banksite [--force]` |
| Private Banking в 2ГИС | `discover-all --source 2gis-private` |

## Что переиспользовано из AuditLens и что нет

- **Переиспользовано:**
  - стек: httpx, SQLAlchemy, Playwright;
  - подход к адаптерам: `sources/base.py`;
  - распознавание капчи и бережное закрытие браузера: `collectors/browser.py`.
- **Не тронуто.** Действующие модули и бизнес-логика.
- **Не перенесено:** маскировка автоматизации (`_STEALTH_JS`, `playwright-stealth`). При блокировке сборщик останавливается и фиксирует это, а не маскируется. Браузерный путь для Яндекса не понадобился: сервис отзывов работает по HTTP.
