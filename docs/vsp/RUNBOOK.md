# Сборщик отзывов о ВСП: запуск

## Локально

```bash
cd al-reviews                      # корень репозитория AuditLens
export PYTHONPATH=src
export VSP_DB_URL=sqlite:///workspace/vsp/vsp_reviews.sqlite   # по умолчанию так и есть
export VSP_AUTHOR_SALT=$(cat workspace/vsp/.author_salt)       # соль для ссылок на авторов, не коммитить

# пилот: реестр ЦБ → 2ГИС → Яндекс → привязка → сбор → отчёт (~30 отделений)
.venv/bin/python -m bank_audit.vsp pilot --out workspace/vsp/pilot

# пилот прервался после 2ГИС — продолжить с шага Яндекса (реестр и 2ГИС из pilot_selection.json)
.venv/bin/python -m bank_audit.vsp pilot --out workspace/vsp/pilot --from-step yandex

# по шагам
.venv/bin/python -m bank_audit.vsp discover --source 2gis --city Казань
.venv/bin/python -m bank_audit.vsp match
.venv/bin/python -m bank_audit.vsp sync --source 2gis --city Казань            # полный проход
.venv/bin/python -m bank_audit.vsp sync --source 2gis --city Казань --mode new # только новые
.venv/bin/python -m bank_audit.vsp sync --source yandex --id 1050330773        # одно отделение
.venv/bin/python -m bank_audit.vsp report --out workspace/vsp/COMPLETENESS.md
.venv/bin/python -m bank_audit.vsp export --out workspace/vsp/reviews.jsonl --source 2gis
```

Тесты: `PYTHONPATH=src .venv/bin/python -m pytest -q tests/vsp`. Сеть они не используют.

## На сервере

Сборщик работает отдельным контейнером из образа приложения. Код модуля примонтирован из своей папки, так что ни приложение, ни образ не пересобираются и не перезапускаются. Данные лежат в отдельной базе PostgreSQL, в схеме `vsp`.

**Раскладка на сервере** (`~/vsp`):

| Путь | Что |
|---|---|
| `src/bank_audit/` | Код модуля: `__init__.py` и `vsp/`. Обновляется распаковкой архива `src/bank_audit/{__init__.py,vsp}` |
| `vsp.env` | Переменные: `VSP_DB_URL` (отдельная база, `…/vsp_reviews?options=-csearch_path%3Dvsp`), `VSP_DB_SCHEMA=vsp`, `VSP_AUTHOR_SALT`, `VSP_LOG_DIR=/vsp/logs`, `VSP_YANDEX_SIGNED_API=1`, частоты. Права 600, значения не печатать |
| `.author_salt` | Соль хэша авторов. Создаётся один раз, не меняется |
| `logs/vsp.log` | Журнал с ротацией: 5 × 10 Мбайт |

**Требования к базе.** Модуль работает с любой базой PostgreSQL, где у роли есть право создать схему. В управляемом облачном PostgreSQL создавать объекты в `public` нельзя даже владельцу базы. Поэтому своя схема (`VSP_DB_SCHEMA`) создаётся при первом запуске, таблицы — тоже. Если позже появятся новые столбцы, они добавятся сами: только `ADD COLUMN`, с `lock_timeout`.

**Демон** — сбор и дописывание по расписанию, работает постоянно:

```bash
docker run -d --name al-vsp --restart unless-stopped --no-healthcheck --network host --user $(id -u):$(id -g) -e HOME=/tmp \
  --env-file ~/vsp/vsp.env -v ~/vsp:/vsp -e PYTHONPATH=/vsp/src -w /vsp \
  --log-opt max-size=20m --log-opt max-file=2 --memory 1g --cpus 1 \
  --entrypoint python auditlens:prod -m bank_audit.vsp daemon --i-know-this-is-mass
```

**Наблюдение и разовые команды** — тот же образ с `--rm`:

```bash
docker run --rm --network host --user $(id -u):$(id -g) -e HOME=/tmp --env-file ~/vsp/vsp.env \
  -v ~/vsp:/vsp -e PYTHONPATH=/vsp/src -w /vsp --entrypoint python auditlens:prod -m bank_audit.vsp status
tail -f ~/vsp/logs/vsp.log          # прогресс: «N/M отделений, … запроса/с, осталось ~X ч»
```

**Обновить код:** распаковать новый архив в `~/vsp/src`, затем `docker restart al-vsp`. Прерванные проходы продолжатся с курсора, обходы — с сохранённого прогресса.

**Остановить:** `docker stop al-vsp`. Данные и прогресс остаются в базе.

### Что делает демон

- **Реестр ЦБ — раз в сутки.** Новые ВСП добавляются. Пропавшие из списка ЦБ получают `closed` — с защитой от неполной выгрузки.
- **Поиск отделений — раз в месяц, с продолжением после остановки:**
  - 2ГИС — все ~1 100 населённых пунктов;
  - Яндекс — страница сети вокруг каждой карточки 2ГИС или ВСП с координатами, если рядом ещё нет найденной карточки;
  - после поиска — привязка к реестру.
- **Привязка — каждые 6 часов,** вместе с пересчётом форматов ВСП.
- **Private Banking в 2ГИС — раз в месяц:** отдельная организация банка, один поиск на проект 2ГИС.
- **Паспорт ВСП с сайта банка — раз в месяц** (если задан `VSP_BANK_SITE`). Обычный браузер открывает страницу офисов и запрашивает плитки карты, где у нас есть ВСП: ~600 запросов, один в 2 секунды. Сайт закрыт проверкой для простых HTTP-клиентов; браузер проходит её сам, как посетитель, без маскировки. Капча или отказ — пауза источника.
- **Сбор по каждому источнику — по расписанию отделения** (`Store.due`):
  - новая карточка получает полный проход;
  - дальше — «только новые», с частотой по живости отделения: ожидаем ~1 новый отзыв к следующей проверке, но не реже раза в двое суток и не чаще раза в 6 часов;
  - полный проход раз в 30 дней (правки, ответы банка, пропавшие отзывы) с разбросом до трёх суток по отделениям.
- **Стоимость проверки «только новых»:**
  - 2ГИС — один запрос;
  - Яндекс с подписью — один JSON-запрос: сессия со страницы одной организации годится для отзывов любых других, и страница грузится раз в 20 минут.
- **Блокировка** (капча, 401/403): источник встаёт на паузу на 3 часа, частота снижается в 0,7 раза. Новая частота хранится в базе (`vsp_kv`, `rps:<источник>`). Капчу сборщик не решает, прокси не меняет.

| Настройка | По умолчанию | Смысл |
|---|---|---|
| `VSP_DUE_TARGET` | 1 | Сколько новых отзывов ожидаем к следующей проверке |
| `VSP_DUE_MIN_H` / `VSP_DUE_MAX_H` | 6 / 48 | Самый частый и самый редкий интервал проверки «только новых» |
| `VSP_FULL_EVERY_D` | 30 | Полный проход отделения |
| `VSP_RETRY_H` | 6 | Повтор после сбоя отделения |
| `VSP_REGISTRY_EVERY_H` / `VSP_DISCOVER_EVERY_D` / `VSP_MATCH_EVERY_H` | 24 / 30 / 6 | Обслуживание |
| `VSP_PAUSE_ON_BLOCK_H` / `VSP_BACKOFF_FACTOR` / `VSP_MIN_RPS` | 3 / 0,7 / 0,1 | Поведение при блокировке |
| `VSP_BANK_SITE` | пусто | Адрес публичного сайта банка для паспорта ВСП (форматы, часы, услуги). Пусто — шаг выключен. Задаётся только на сервере |
| `VSP_BANK_SITE_RPS` / `VSP_BANK_SITE_EVERY_D` | 0,5 / 30 | Частота запросов к сайту банка и период обхода |
| `VSP_DAEMON_BATCH` / `VSP_DAEMON_SLEEP_S` | 200 / 600 | Порция отделений за цикл; пауза, когда делать нечего |

### Чтение моделью

Демон читает новые отзывы моделью сам — если ему доступны `LLM_BASE_URL` и `LLM_API_KEY` (те же, что у приложения):

| Переменная | По умолчанию | Что задаёт |
|---|---|---|
| `VSP_LLM_ENABLED` | 1 | 0 — шаг чтения выключен (расчёт вкладки идёт без него) |
| `VSP_LLM_EVERY_H` | 1 | Как часто читать новые отзывы |
| `VSP_LLM_DAILY_RUB` | 300 | Потолок трат на модели в сутки (чтение, почерки, выводы по отделениям) |
| `VSP_LLM_STEP_LIMIT` | 3000 | Отзывов на один шаг и этап |
| `VSP_LLM_STALE_H` | 26 | Сколько часов отзывы могут ждать чтения, прежде чем сторож поднимет тревогу |
| `VSP_LLM_TPM` | 70000 | Расход токенов в минуту на модель (лимит облака — 100 тыс.) |
| `VSP_LLM_DETAIL_SINCE` | 2021-01-01 | С какой даты тяжёлые истории уточняются (тип, кому выгода); с неё же считаются волны и очаги |
| `VSP_HQ_CODES` | 9038/1919 | Коды карточек центрального офиса: в сравнении отделений не участвуют |

Разовый запуск всей цепочки (чтение → почерки → расчёт → выводы → расчёт): `python -m bank_audit.vsp nightly --cap-rub 300`.

Сколько это стоит (замер 10–11.11.2026, DeepSeek V4.1 Flash): уточнение тяжёлой истории ≈ 0,23 ₽; редактор почерков ≈ 2,4 ₽ за вызов (40 описаний) — первый полный каталог на 5 тыс. историй обошёлся в ≈ 460 ₽, дальше по ночам рубли; вывод по отделению ≈ 0,8 ₽ — первые 594 отделения ≈ 470 ₽, дальше перечитываются только отделения, где изменился состав историй. Потолок `--cap-rub` проверяется между вызовами, поэтому параллельные вызовы могут выйти за него на 10–15 %.

Ручной `signals` днём ставит отметку «расчёт был» (`signals:at`), и ближайшей ночью демон цепочку пропустит: ночной расчёт идёт, только если отметке больше 22 часов. Если нужен и ручной расчёт, и ночной — после ручного верните отметку назад: `Store(...).kv_set("signals:at", "<вчерашняя дата>T19:30:00+00:00")`.

Раньше новые отзывы читал внешний цикл `~/vsp/llm_loop.sh`. С 11.11.2026 он остановлен и больше не нужен: он запускал расчёт и команду `schemes`, которой в новом коде нет. Не запускать.
Что с чтением сейчас — `python -m bank_audit.vsp status`, ключ `llm`: `ok`, `late` (отзывы ждут дольше суток) или `off` (шаг ещё не шёл).

## Долгое ожидание (раздел «Ожидание»)

Очереди в тяжёлые истории не входят: этап отбора считает их шумом. У них свой этап чтения —
`signals/wait.py`, версия ответа `w1` в той же таблице `vsp_review_llm`.

- **Кто читает.** Шаг демона после чтения историй, раз в час. Кандидаты — жалобы (оценка 1–3) не старше
  `VSP_WAIT_SINCE` (по умолчанию 2024-01-01) со словами об очереди и ожидании; слова отсеивает база.
  Каждого кандидата читает модель отбора (`VSP_WAIT_MODEL`, по умолчанию та же, что `VSP_LLM_SCREEN_MODEL`):
  жалоба ли это на ожидание в отделении, сколько клиент ждал, причина, ушёл ли, дословная цитата.
- **Сколько стоит.** ≈ 0,014 ₽ за жалобу (замер 12.11.2026). Первое чтение накопленного с 2024 года —
  около 25 тыс. жалоб, ≈ 350 ₽; дальше — десятки жалоб в день. Траты идут в общий суточный потолок
  `VSP_LLM_DAILY_RUB`; за один шаг читается не больше `VSP_WAIT_STEP_LIMIT` (8000).
- **Вручную:** `python -m bank_audit.vsp wait --limit 5000 --cap-rub 100`. Прочитанное не перечитывается.
- **Что в журнале и в базе.** Строки «ожидание: …» в `vsp.log`; итог шага — ключ `wait:last` в `vsp_kv`.
  Сторож чтения историй (`llm:last`) этот этап не учитывает: накопленное за прошлые годы читается не один
  час и не должно выглядеть как отставание.
- **Качество** (две случайные выборки, 280 жалоб, прочитаны вручную 12.11.2026): из отмеченных моделью по
  делу 96 %, из настоящих жалоб на ожидание найдено около 94 %.
- **Раздел** считает по этим ответам вживую (`web/vsp_wait.py`, кэш 10 минут), ночной расчёт ему не нужен.
  Знаменатель — все жалобы с текстом за период: «доля жалоб на ожидание среди жалоб отделения» против доли
  по остальной сети, точный биномиальный тест с поправкой на число отделений.

## Ежедневное письмо раздела

`web/vsp_mail.py`. Подписку человек включает сам — кнопка «Письма на почту» в разделе или строка
«Аудит сети ВСП» в настройках колокольчика; настройка лежит в профиле (`app_user.prefs.vsp_mail`:
включено, регионы, что присылать).

- **Когда.** В рабочие дни с `VSP_MAIL_HOUR_MSK` (9) до `VSP_MAIL_LAST_HOUR_MSK` (14) по Москве, тот же
  фоновый цикл, что у остальных писем. В понедельник — за выходные. Нового нет — письма нет (в журнале
  `app_mail_log` строка `vsp_daily` с пометкой «нечего отправлять»).
- **Что.** Новые тяжёлые истории (до пяти самых важных), новые жалобы на ожидание (числа и до пяти примеров),
  способы действия, которые появились или стали расти. «Новое» считается выпусками: таблица `vsp_mail_item`
  (миграция 114) хранит, в каком выпуске запись появилась впервые; подписчик получает выпуски после своего
  прошлого письма.
- **Кому.** Только тем, кому раздел открыт, — доступ проверяется при каждой отправке. На некорпоративный
  адрес уходят только числа и ссылка.
- **Отписаться.** Ссылка «Отписаться» в письме открывает раздел и выключает подписку; то же — в окне
  «Письма» и в колокольчике.
- **Пример себе.** Кнопка «Прислать пример сейчас» (не чаще трёх раз в день, в журнале — `vsp_test`).
- Перед выкладкой кода применить миграцию `114_vsp_daily_mail.sql`.

## Что делать, если…

- **`blocked` в отчёте.** Источник показал капчу или 401/403. Сборщик остановил источник в этом прогоне. Повторить позже и с меньшей частотой (`VSP_*_RPS`). Обходить защиту не нужно.
- **`below_declared` у 2ГИС.** Источник заявляет больше, чем отдаёт. Обычно это скрытые модерацией отзывы, они не видны никому.
- **`window` у Яндекса.** У отделения больше 600 отзывов, по умолчанию берём 600. Режим с подписью даёт около 68%.
- **Плашка «модель отстаёт с чтением» во вкладке.** Смотреть `status` → `llm`: исчерпан дневной потолок (`spent_today` ≥ `daily_cap`), нет ключа модели у демона или шаг падает (`failed`). Поднять потолок — `VSP_LLM_DAILY_RUB`; дочитать разом — `llm-read --stage all --limit 20000 --cap-rub N`.
- **Прерван прогон.** Запустить ту же команду: незавершённые отделения продолжатся с сохранённого курсора.
- **`conflict` в привязке.** Это не ошибка, а отказ склеивать. Причины: два ВСП по одному адресу; номер ЦБ в карточке указывает на передвижной пункт, КИЦ или другой город; соперничающие карточки в одном здании. Разбирается вручную, `match_status=confirmed` закрепляет решение — повторный `match` его не трогает.

## Кому открыт раздел

Раздел закрыт для всех, кроме владельца (`ADMIN_USERS`), пока его не открыли:

- по логину — `VSP_USERS` в окружении или список `users` в настройке `vsp_users` (`app_setting`);
- подразделению целиком — список `units` в той же настройке: номера подразделений из штата
  (`org_member`, штат загружается в «Пульсе»). Так раздел получают и те, кто в AuditLens ещё ни разу
  не заходил: логина у них нет, а в штате они есть. Человек сопоставляется со штатом по табельному
  номеру в конце логина; если такого номера в штате нет — по имени и фамилии, когда они в штате
  единственные. Уволенные доступа не получают.

Менять удобнее всего в «Пульсе»: раздел «Сеть ВСП» (виден только владельцу) → «Кому открыт раздел» —
переключатели подразделений и отдельные люди. Там же видно, кто заходит в раздел, сколько времени
проводит и что открывает (досье отделений, карточки способов действия, полные отзывы, выгрузки).

То же без интерфейса — владельцу, без перезапуска: `POST /api/vsp/beta` с `{"users": [...]}` и (или)
`{"units": [...]}`; непереданное не меняется. `GET /api/vsp/beta` показывает оба списка и сколько
человек с доступом уже заходили. Настройка перечитывается раз в минуту.
